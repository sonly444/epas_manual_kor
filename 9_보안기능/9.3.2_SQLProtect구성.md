# SQL/Protect 구성 (Configuring SQL/Protect) — EPAS 18

> 원문: [EPAS v18 — Security guide › Protecting against SQL injection attacks › Configuring SQL/Protect](https://www.enterprisedb.com/docs/epas/latest/epas_security_guide/02_protecting_against_sql_injection_attacks/02_configuring_sql_protect/)
> EPAS v18 공식 문서의 한글 **전문 번역**입니다. 파라미터·함수·명령·SQL·출력은 원문 그대로 보존했습니다.

SQL/Protect의 동작 방식을 구성할 수 있습니다.

## 전제 조건 (Prerequisites)

SQL/Protect를 구성하기 전에 다음 전제 조건을 충족하십시오.

- SQL/Protect 실행에 필요한 라이브러리 파일(Linux에서는 `sqlprotect.so`, Windows에서는 `sqlprotect.dll`)이 EDB Postgres Advanced Server 홈 디렉터리의 `lib` 하위 디렉터리에 설치되어 있어야 합니다. Windows의 경우 EDB Postgres Advanced Server 인스톨러가 이를 수행합니다. Linux의 경우 `edb-as<xx>-server-sqlprotect` RPM 패키지를 설치합니다(여기서 `<xx>`는 EDB Postgres Advanced Server 버전 번호).

- EDB Postgres Advanced Server 홈 디렉터리의 `share/contrib` 하위 디렉터리에 있는 SQL 스크립트 파일 `sqlprotect.sql`이 필요합니다.

- 데이터베이스 서버가 SQL/Protect를 사용하도록 구성해야 하며, SQL/Protect가 모니터링할 각 데이터베이스를 구성해야 합니다.

  - SQL/Protect가 사용하는 구성 파라미터를 추가하고 활성화하여 데이터베이스 서버 구성 파일 `postgresql.conf`를 수정해야 합니다.
  - SQL/Protect가 모니터링할 각 데이터베이스에 SQL/Protect가 사용하는 데이터베이스 객체를 설치합니다.

## 모듈 구성 (Configuring the module)

1. EDB Postgres Advanced Server 홈 디렉터리의 `data` 하위 디렉터리에 있는 `postgresql.conf` 파일에서 다음 구성 파라미터를 편집합니다.

- `shared_preload_libraries`. 라이브러리 목록에 `$libdir/sqlprotect`를 추가합니다.

- `edb_sql_protect.enabled`. SQL/Protect가 보호된 역할이 발행하는 SQL 구문을 분석하고 `edb_sql_protect.level` 설정에 따라 반응하여, 보호된 역할을 능동적으로 모니터링할지 여부를 제어합니다. SQL/Protect로 모니터링을 시작할 준비가 되면 이 파라미터를 `on`으로 설정합니다. 기본값은 `off`입니다.

- `edb_sql_protect.level`. 보호된 역할이 SQL 구문을 발행할 때 SQL/Protect가 취하는 동작을 설정합니다. 기본 동작은 `passive`입니다. 처음에는 이 파라미터를 `learn`으로 설정합니다. 자세한 내용은 아래 "보호 수준 설정"을 참고하십시오.

- `edb_sql_protect.max_protected_roles`. 보호할 역할의 최대 수를 설정합니다. 기본값은 `64`입니다.

- `edb_sql_protect.max_protected_relations`. 역할당 보호할 릴레이션의 최대 수를 설정합니다. 기본값은 `1024`입니다.

서버의 총 보호된 릴레이션 수는 보호된 릴레이션 수에 보호된 역할 수를 곱한 값입니다. 모든 보호된 릴레이션은 공유 메모리 공간을 소비합니다. 가능한 최대 보호된 릴레이션을 위한 공간은 데이터베이스 서버 시작 중에 예약됩니다.

- `edb_sql_protect.max_queries_to_save`. `edb_sql_protect_queries` 뷰에 저장할 위반 쿼리의 최대 수를 설정합니다. 기본값은 `5000`입니다. 위반 쿼리 수가 한도에 도달하면 추가 쿼리는 뷰에 저장되지 않지만 데이터베이스 서버 로그 파일에서 접근할 수 있습니다.

이 파라미터의 유효한 최솟값은 `100`입니다. `100`보다 작은 값을 지정하면 데이터베이스 서버는 기본 설정인 `5000`을 사용하여 시작합니다. 경고 메시지가 데이터베이스 서버 로그 파일에 기록됩니다.

이 예는 `postgresql.conf` 파일에서 이러한 파라미터의 설정을 보여줍니다.

```ini
shared_preload_libraries = '$libdir/dbms_pipe,$libdir/edb_gen,$libdir/sqlprotect'
                                        # (change requires restart)
                          .
                          .
                          .
edb_sql_protect.enabled = off
edb_sql_protect.level = learn
edb_sql_protect.max_protected_roles = 64
edb_sql_protect.max_protected_relations = 1024
edb_sql_protect.max_queries_to_save = 5000
```

2. `postgresql.conf` 파일을 수정한 후 데이터베이스 서버를 재시작합니다.

- **Linux의 경우:** `restart` 옵션으로 EDB Postgres Advanced Server 서비스 스크립트를 호출합니다.

Redhat 또는 CentOS 7.x 설치에서는 다음 명령을 사용합니다.

```shell
systemctl restart edb-as-18
```

- **Windows의 경우:** Windows Services 애플릿을 사용하여 `edb-as-14`라는 서비스를 재시작합니다.

3. SQL 인젝션 공격으로부터 보호할 각 데이터베이스에 대해, 슈퍼유저(설치 옵션에 따라 `enterprisedb` 또는 `postgres`)로 데이터베이스에 연결합니다. 그런 다음 EDB Postgres Advanced Server 홈 디렉터리의 `share/contrib` 하위 디렉터리에 있는 스크립트 `sqlprotect.sql`을 실행합니다. 이 스크립트는 `sqlprotect`라는 스키마에 SQL/Protect 데이터베이스 객체를 생성합니다.

이 예는 `edb`라는 데이터베이스에 대한 보호를 설정하는 과정을 보여줍니다.

## 보호할 역할 선택 (Selecting roles to protect)

데이터베이스에 SQL/Protect 데이터베이스 객체를 생성한 후, 보호를 위해 SQL 쿼리를 모니터링할 역할과 각 역할에 할당할 보호 수준을 선택할 수 있습니다.

### 보호된 역할 목록 설정 (Setting the protected roles list)

보호할 각 데이터베이스에 대해, 모니터링할 역할을 결정한 다음 해당 데이터베이스의 *보호된 역할 목록(protected roles list)*에 그 역할을 추가해야 합니다.

1. `psql` 또는 Postgres Enterprise Manager 클라이언트로 보호할 데이터베이스에 슈퍼유저로 연결합니다.

```sql
$ /usr/edb/as18/bin/psql -d edb -U enterprisedb
Password for user enterprisedb:
psql.bin (18.1.0, server 18.1.0)
Type "help" for help.

edb=#
```

2. SQL/Protect 테이블, 함수, 뷰는 `sqlprotect` 스키마 아래에 빌드되므로, `SET search_path` 명령을 사용하여 검색 경로에 `sqlprotect` 스키마를 포함합니다. 이렇게 하면 SQL/Protect 데이터베이스 객체와 관련된 작업이나 쿼리에서 스키마를 한정할 필요가 없어집니다.

```sql
edb=# SET search_path TO sqlprotect;
SET
```

3. 보호하려는 각 역할을 보호된 역할 목록에 추가해야 합니다. 이 목록은 `edb_sql_protect` 테이블에 유지됩니다.

역할을 추가하려면 `protect_role('rolename')` 함수를 사용합니다. 이 예는 `appuser`라는 역할을 보호합니다.

```sql
edb=# SELECT protect_role('appuser');
```

출력

```text
 protect_role
--------------

(1 row)
```

다음 쿼리로 보호된 역할 목록에 추가된 역할을 나열할 수 있습니다.

```sql
edb=# SELECT * FROM edb_sql_protect;
```

출력

```text
 dbid  | roleid | protect_relations | allow_utility_cmds | allow_tautology |
 allow_empty_dml
-------+--------+-------------------+--------------------+-----------------+--
-------------
 13917 |  16671 | t                 | f                  | f               | f
(1 row)
```

객체 식별 번호(OID) 대신 객체 이름을 사용하여 동일한 정보를 제공하는 뷰도 제공됩니다.

```sql
edb=# \x
Expanded display is on.
edb=# SELECT * FROM list_protected_users;
```

출력

```text
-[ RECORD 1 ]------+--------
dbname             | edb
username           | appuser
protect_relations  | t
allow_utility_cmds | f
allow_tautology    | f
allow_empty_dml    | f
```

### 보호 수준 설정 (Setting the protection level)

`edb_sql_protect.level` 구성 파라미터는 보호된 역할이 SQL 구문을 발행할 때 SQL/Protect의 동작을 정의하는 보호 수준을 설정합니다. 정의된 동작은 데이터베이스 서버에서 SQL/Protect로 구성된 모든 데이터베이스의 보호된 역할 목록에 있는 모든 역할에 적용됩니다.

`postgresql.conf` 파일에서 `edb_sql_protect.level` 구성 파라미터를 다음 값 중 하나로 설정하여 학습, 수동, 능동 모드를 지정할 수 있습니다.

- `learn`. 보호된 역할의 활동을 추적하고 역할이 사용하는 릴레이션을 기록합니다. SQL/Protect를 처음 구성할 때 이 모드를 사용하여 보호되는 애플리케이션의 예상 동작을 학습합니다.
- `passive`. 보호된 역할이 정의된 규칙을 위반하면 경고를 발행하지만 SQL 구문의 실행을 중단하지는 않습니다. 이 모드는 SQL/Protect가 보호된 역할의 예상 동작을 학습한 후의 다음 단계입니다. 본질적으로 침입 탐지(intrusion detection) 모드로 동작합니다. 적절한 모니터링이 마련되어 있으면 이 모드를 프로덕션에서 실행할 수 있습니다.
- `active`. 보호된 역할에 대해 모든 유효하지 않은 구문을 중단합니다. 이 모드는 SQL 방화벽처럼 동작하여 위험한 쿼리의 실행을 방지합니다. 이 접근 방식은 공격자가 취약점 지점과 애플리케이션 뒤에 있는 데이터베이스 유형을 찾으려는 초기 침투 테스트에 특히 효과적입니다. SQL/Protect는 이러한 취약점 지점을 닫을 뿐 아니라 차단된 쿼리를 추적합니다. 이 추적은 공격자가 시스템을 침투할 다른 방법을 찾기 전에 관리자에게 경고할 수 있습니다.

기본 모드는 `passive`입니다.

SQL/Protect를 처음 사용하는 경우 `edb_sql_protect.level`을 `learn`으로 설정합니다.

## 보호된 역할 모니터링 (Monitoring protected roles)

데이터베이스에서 SQL/Protect를 구성하고, 보호된 역할 목록에 역할을 추가하고, 원하는 보호 수준을 설정한 후, SQL/Protect를 `learn`, `passive`, `active` 모드로 활성화할 수 있습니다. 그런 다음 애플리케이션 실행을 시작할 수 있습니다.

새 SQL/Protect 설치에서 첫 번째 단계는 정상 작동 중에 보호된 역할이 접근할 수 있는 릴레이션을 결정하는 것입니다. 학습 모드는 역할이 애플리케이션을 실행하는 동안 SQL/Protect가 접근되는 릴레이션을 기록할 수 있게 합니다. 이들은 `edb_sql_protect_rel` 테이블에 저장된 역할의 *보호된 릴레이션 목록(protected relations list)*에 추가됩니다.

공격에 대한 보호 모니터링은 SQL/Protect를 수동 또는 능동 모드로 실행할 때 시작됩니다. 수동 및 능동 모드에서 역할은 보호된 릴레이션 목록에 있는 릴레이션에 접근할 수 있습니다. 이들은 일반적인 사용 중에 역할이 접근할 수 있는 지정된 릴레이션입니다.

그러나 역할이 보호된 릴레이션 목록에 없는 릴레이션에 접근하려고 하면, SQL/Protect는 `WARNING` 또는 `ERROR` 심각도 수준의 메시지를 반환합니다. 모드가 수동인지 능동인지에 따라 릴레이션에 대한 역할의 시도된 작업이 수행되지 않을 수 있습니다.

### 학습 모드 (Learn mode)

SQL/Protect를 학습 모드로 활성화하려면 다음과 같이 합니다.

1. `postgresql.conf` 파일에서 파라미터를 설정합니다.

```ini
edb_sql_protect.enabled = on
edb_sql_protect.level = learn
```

2. `postgresql.conf` 파일을 다시 로드합니다. EDB Postgres Advanced Server 애플리케이션 메뉴에서 **Reload Configuration > Expert Configuration**을 선택합니다.

구성 파일을 다시 로드하는 다른 방법으로, `pg_reload_conf` 함수를 사용합니다. 슈퍼유저로 데이터베이스에 연결되어 있는지 확인하고 `pg_reload_conf` 함수를 실행합니다.

```sql
edb=# SELECT pg_reload_conf();
```

출력

```text
 pg_reload_conf
----------------
 t
(1 row)
```

3. 보호된 역할이 애플리케이션을 실행하도록 허용합니다.

예를 들어 다음 쿼리는 보호된 역할 `appuser`가 `psql` 애플리케이션에서 발행합니다.

```sql
edb=> SELECT * FROM dept;
```

출력

```text
NOTICE:  SQLPROTECT: Learned relation: 16384
 deptno |   dname    |   loc
--------+------------+----------
     10 | ACCOUNTING | NEW YORK
     20 | RESEARCH   | DALLAS
     30 | SALES      | CHICAGO
     40 | OPERATIONS | BOSTON
(4 rows)
```

```sql
edb=> SELECT empno, ename, job FROM emp WHERE deptno = 10;
```

출력

```text
NOTICE:  SQLPROTECT: Learned relation: 16391
 empno | ename  |    job
-------+--------+-----------
  7782 | CLARK  | MANAGER
  7839 | KING   | PRESIDENT
  7934 | MILLER | CLERK
(3 rows)
```

SQL/Protect는 릴레이션이 역할의 보호된 릴레이션 목록에 추가되었음을 나타내는 `NOTICE` 심각도 수준의 메시지를 생성합니다.

SQL/Protect 학습 모드에서는 의심스러운 SQL 구문의 실행이 방지되지 않습니다. 그러나 잠재적으로 위험한 구문에 대해 사용자에게 알리는 메시지가 발행됩니다.

```sql
edb=> CREATE TABLE appuser_tab (f1 INTEGER);
NOTICE: SQLPROTECT: This command type is illegal for this user
CREATE TABLE
edb=> DELETE FROM appuser_tab;
NOTICE: SQLPROTECT: Learned relation: 16672
NOTICE: SQLPROTECT: Illegal Query: empty DML
DELETE 0
```

4. 보호된 역할이 애플리케이션을 실행하는 동안, SQL/Protect 테이블을 쿼리하여 릴레이션이 역할의 보호된 릴레이션 목록에 추가되었는지 확인할 수 있습니다. 모니터링 중인 데이터베이스에 슈퍼유저로 연결하고, 검색 경로에 `sqlprotect` 스키마를 포함하도록 설정합니다.

```sql
edb=# SET search_path TO sqlprotect;
SET
```

`edb_sql_protect_rel` 테이블을 쿼리하여 보호된 릴레이션 목록에 추가된 릴레이션을 확인합니다.

```sql
edb=# SELECT * FROM edb_sql_protect_rel;
```

출력

```text
 dbid   | roleid | relid
--------+--------+-------
 13917  | 16671  | 16384
 13917  | 16671  | 16391
 13917  | 16671  | 16672
(3 rows)
```

`list_protected_rels` 뷰는 OID 대신 객체 이름과 함께 더 포괄적인 정보를 제공합니다.

```sql
edb=# SELECT * FROM list_protected_rels;
```

출력

```text
 Database | Protected User | Schema |    Name     | Type  |    Owner
----------+----------------+--------+-------------+-------+------------
 edb      | appuser        | public | dept        | Table | enterprisedb
 edb      | appuser        | public | emp         | Table | enterprisedb
 edb      | appuser        | public | appuser_tab | Table | appuser
(3 rows)
```

### 수동 모드 (Passive mode)

역할의 애플리케이션이 필요한 모든 릴레이션에 접근한 후, 보호 수준을 변경하여 SQL/Protect가 들어오는 SQL 쿼리를 능동적으로 모니터링하고 SQL 인젝션 공격으로부터 보호하도록 할 수 있습니다.

수동 모드는 능동 모드보다 덜 제한적인 보호 모드입니다.

1. SQL/Protect를 수동 모드로 활성화하려면 `postgresql.conf` 파일에서 다음 파라미터를 설정합니다.

```ini
edb_sql_protect.enabled = on
edb_sql_protect.level = passive
```

2. "학습 모드"의 2단계에 표시된 대로 구성 파일을 다시 로드합니다.

이제 SQL/Protect는 수동 모드입니다. 앞 예제의 `dept`와 `emp` 테이블처럼 학습된 릴레이션에 대해서는 SQL 구문이 허용됩니다. 사용자 `appuser`가 실행한 다음 쿼리에서 보듯이, SQL/Protect가 클라이언트에 특별히 알릴 필요는 없습니다.

```sql
edb=> SELECT * FROM dept;
```

출력

```text
 deptno |   dname    |   loc
--------+------------+----------
    10  | ACCOUNTING | NEW YORK
    20  | RESEARCH   | DALLAS
    30  | SALES      | CHICAGO
    40  | OPERATIONS | BOSTON
(4 rows)
```

```sql
edb=> SELECT empno, ename, job FROM emp WHERE deptno = 10;
```

출력

```text
 empno | ename  |    job
-------+--------+-----------
  7782 | CLARK  | MANAGER
  7839 | KING   | PRESIDENT
  7934 | MILLER | CLERK
(3 rows)
```

SQL/Protect는 어떤 SQL 구문의 실행도 방지하지 않습니다. 그러나 학습되지 않은 릴레이션에 대해 실행된 SQL 구문에 대해서는 `WARNING` 심각도 수준의 메시지를 발행합니다. 금지된 시그니처를 포함하는 SQL 구문에 대해서도 경고를 발행합니다.

```sql
edb=> CREATE TABLE appuser_tab_2 (f1 INTEGER);
WARNING: SQLPROTECT: This command type is illegal for this user
CREATE TABLE
edb=> INSERT INTO appuser_tab_2 VALUES (1);
WARNING: SQLPROTECT: Illegal Query: relations
INSERT 0 1
edb=> INSERT INTO appuser_tab_2 VALUES (2);
WARNING: SQLPROTECT: Illegal Query: relations
INSERT 0 1
edb=> SELECT * FROM appuser_tab_2 WHERE 'x' = 'x';
WARNING: SQLPROTECT: Illegal Query: relations
WARNING: SQLPROTECT: Illegal Query: tautology
```

출력

```text
f1
----
  1
  2
(2 rows)
```

3. 의심스러운 활동에 대한 통계를 모니터링합니다.

`edb_sql_protect_stats` 뷰를 쿼리하면, 역할의 보호된 릴레이션 목록에 없는 릴레이션을 참조하거나 SQL 인젝션 공격 시그니처를 포함한 SQL 구문이 실행된 횟수를 확인할 수 있습니다.

다음은 `edb_sql_protect_stats`에 대한 쿼리입니다.

```sql
edb=# SET search_path TO sqlprotect;
SET
edb=# SELECT * FROM edb_sql_protect_stats;
```

출력

```text
 username  | superusers | relations | commands | tautology | dml
-----------+------------+-----------+----------+-----------+-----
 appuser   |     0      |     3     |    1     |     1     | 0
(1 row)
```

4. 특정 공격에 대한 정보를 봅니다.

`edb_sql_protect_queries` 뷰를 쿼리하면, 역할의 보호된 릴레이션 목록에 없는 릴레이션을 참조하거나 SQL 인젝션 공격 시그니처를 포함하여 실행된 SQL 구문을 확인할 수 있습니다.

다음 코드 샘플은 `edb_sql_protect_queries`에 대한 쿼리를 보여줍니다.

### 능동 모드 (Active mode)

능동 모드에서는 허용되지 않는 SQL 구문의 실행이 방지됩니다. 또한 SQL/Protect가 발행하는 메시지는 `WARNING` 대신 `ERROR`의 더 높은 심각도 수준을 갖습니다.

1. SQL/Protect를 능동 모드로 활성화하려면 `postgresql.conf` 파일에서 다음 파라미터를 설정합니다.

```ini
edb_sql_protect.enabled = on
edb_sql_protect.level = active
```

2. "학습 모드"의 2단계에 표시된 대로 구성 파일을 다시 로드합니다.

이 예는 "수동 모드"의 2단계 예제와 유사한 SQL 구문을 보여줍니다. 이 구문들은 `edb_sql_protect.level`이 `active`로 설정된 경우 사용자 `appuser`가 실행합니다.

```sql
edb=> CREATE TABLE appuser_tab_3 (f1 INTEGER);
ERROR: SQLPROTECT: This command type is illegal for this user
edb=> INSERT INTO appuser_tab_2 VALUES (1);
ERROR: SQLPROTECT: Illegal Query: relations
edb=> SELECT * FROM appuser_tab_2 WHERE 'x' = 'x';
ERROR: SQLPROTECT: Illegal Query: relations
```

다음은 결과 통계를 보여줍니다.

```sql
edb=# SELECT * FROM sqlprotect.edb_sql_protect_stats;
```

```text
-----------+------------+-----------+----------+-----------+-----
 appuser   |      0     |     5     |     2    |     1     | 0
(1 row)
```
