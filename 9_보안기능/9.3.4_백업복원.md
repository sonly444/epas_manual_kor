# SQL/Protect 데이터베이스 백업 및 복원 (Backing up and restoring a SQL/Protect database) — EPAS 18

> 원문: [EPAS v18 — Security guide › Protecting against SQL injection attacks › Backing up and restoring a SQL/Protect database](https://www.enterprisedb.com/docs/epas/latest/epas_security_guide/02_protecting_against_sql_injection_attacks/04_backing_up_restoring_sql_protect/)
> EPAS v18 공식 문서의 한글 **전문 번역**입니다. 함수·명령·SQL·출력은 원문 그대로 보존했습니다.

SQL/Protect로 구성된 데이터베이스를 백업한 후 백업 파일을 새 데이터베이스로 복원하려면, 일반적인 백업·복원 절차와 관련된 고려 사항 외에 추가 고려 사항이 필요합니다. 이러한 추가 고려 사항은 주로 SQL/Protect 테이블에서 객체 식별 번호(OID)를 사용하기 때문입니다.

> **참고**
> 이 정보는 `pg_dump` 백업 프로그램을 사용할 때처럼, 백업·복원 절차의 결과로 새 데이터베이스에서 데이터베이스 객체가 새 OID로 다시 생성되는 경우에 적용됩니다.
>
> 운영체제의 복사 유틸리티를 사용하여 EDB Postgres Advanced Server 데이터 파일의 바이너리 이미지를 생성하는 방식(파일 시스템 백업 방법)으로 EDB Postgres Advanced Server 데이터베이스 서버를 백업하는 경우에는 이 정보가 적용되지 않습니다.

## SQL/Protect 테이블의 객체 식별 번호 (Object identification numbers in SQL/Protect tables)

SQL/Protect는 두 개의 테이블 `edb_sql_protect`와 `edb_sql_protect_rel`을 사용하여 데이터베이스, 역할, 릴레이션과 같은 데이터베이스 객체에 대한 정보를 저장합니다. 이 테이블에서 이러한 데이터베이스 객체에 대한 참조는 객체의 텍스트 이름이 아니라 OID를 사용하여 이루어집니다. OID는 EDB Postgres Advanced Server가 각 데이터베이스 객체를 고유하게 식별하는 데 사용하는 숫자 데이터 타입입니다.

데이터베이스 객체가 생성되면 EDB Postgres Advanced Server는 객체에 OID를 할당하며, 이후 데이터베이스 카탈로그에서 객체에 대한 참조가 필요할 때 이 OID가 사용됩니다. 두 데이터베이스에서 동일한 데이터베이스 객체(예: 동일한 `CREATE TABLE` 구문의 테이블)를 생성하면, 각 테이블에는 각 데이터베이스에서 서로 다른 OID가 할당됩니다.

백업된 데이터베이스 객체를 다시 생성하는 백업·복원 작업에서, 복원된 객체는 원본 데이터베이스에서 할당되었던 것과 다른 OID를 새 데이터베이스에서 갖게 됩니다. 그 결과 `edb_sql_protect`와 `edb_sql_protect_rel` 테이블에 저장된 데이터베이스, 역할, 릴레이션을 참조하는 OID는, 이 테이블들이 백업 파일로 덤프된 후 새 데이터베이스로 복원될 때 더 이상 유효하지 않습니다.

두 함수 `export_sqlprotect`와 `import_sqlprotect`는, SQL/Protect 테이블을 백업·복원하여 테이블이 복원된 후 SQL/Protect 테이블의 OID가 올바른 데이터베이스 객체를 참조하도록 하기 위해 특별히 사용됩니다.

## 데이터베이스 백업 (Backing up the database)

SQL/Protect로 구성된 데이터베이스를 백업합니다.

1. `pg_dump`를 사용하여 백업 파일을 생성합니다.

이 예는 `pg_dump` 유틸리티 프로그램을 사용하여 데이터베이스 `edb`에서 생성한 `/tmp/edb.dmp`라는 평문(plain-text) 백업 파일을 보여줍니다.

```shell
$ cd /usr/edb/as18/bin
$ ./pg_dump -U enterprisedb -Fp -f /tmp/edb.dmp edb
Password:
$
```

2. 슈퍼유저로 데이터베이스에 연결하고, `export_sqlprotect('sqlprotect_file')` 함수를 사용하여 SQL/Protect 데이터를 내보냅니다. `sqlprotect_file`은 SQL/Protect 데이터가 저장되는 파일의 전체 한정 경로입니다.

`enterprisedb` 운영체제 계정(PostgreSQL 호환 모드로 EDB Postgres Advanced Server를 설치한 경우 `postgres`)은 `sqlprotect_file`에 지정된 디렉터리에 대한 읽기·쓰기 권한이 있어야 합니다.

```sql
edb=# SELECT sqlprotect.export_sqlprotect('/tmp/sqlprotect.dmp');
```

출력

```text
 export_sqlprotect
-------------------
(1 row)
```

`/tmp/edb.dmp`와 `/tmp/sqlprotect.dmp` 파일이 전체 데이터베이스 백업을 구성합니다.

## 백업 파일에서 복원 (Restoring from the backup files)

1. 백업 파일을 새 데이터베이스로 복원합니다.

이 예는 `psql` 유틸리티 프로그램을 사용하여 평문 백업 파일 `/tmp/edb.dmp`를 새로 생성된 `newdb`라는 데이터베이스로 복원합니다.

```sql
$ /usr/edb/as18/bin/psql -d newdb -U enterprisedb -f /tmp/edb.dmp
Password for user enterprisedb:
SET
SET
SET
SET
SET
COMMENT
CREATE SCHEMA
    .
    .
    .
```

2. 슈퍼유저로 새 데이터베이스에 연결하고, `edb_sql_protect_rel` 테이블에서 모든 행을 삭제합니다.

이 삭제는 원본 데이터베이스에서 백업된, `edb_sql_protect_rel` 테이블에 있던 기존 행을 제거합니다. 이 행들은 백업 파일이 복원된 데이터베이스를 기준으로 올바른 OID를 포함하지 않습니다.

```sql
$ /usr/edb/as18/bin/psql -d newdb -U enterprisedb
Password for user enterprisedb:
psql.bin (18.1.0, server 18.1.0)
Type "help" for help.

newdb=# DELETE FROM sqlprotect.edb_sql_protect_rel;
DELETE 2
```

3. `edb_sql_protect` 테이블에서 모든 행을 삭제합니다.

이 삭제는 원본 데이터베이스에서 백업된, `edb_sql_protect` 테이블에 있던 기존 행을 제거합니다. 이 행들은 백업 파일이 복원된 데이터베이스를 기준으로 올바른 OID를 포함하지 않습니다.

```sql
newdb=# DELETE FROM sqlprotect.edb_sql_protect;
DELETE 1
```

4. 데이터베이스의 통계를 모두 삭제합니다.

이 삭제는 백업을 복원하는 데이터베이스의 기존 통계를 제거합니다. 다음 쿼리는 기존 통계를 표시합니다.

```sql
newdb=# SELECT * FROM sqlprotect.edb_sql_protect_stats;
```

출력

```text
 username  | superusers | relations | commands | tautology | dml
-----------+------------+-----------+----------+-----------+-----
(0 rows)
```

앞의 쿼리에 나타나는 각 행에 대해, 항목의 역할 이름을 지정하여 `drop_stats` 함수를 사용합니다.

예를 들어 `username` 컬럼에 `appuser`가 있는 행이 나타나면 다음 명령을 발행하여 제거합니다.

```sql
newdb=# SELECT sqlprotect.drop_stats('appuser');
```

출력

```text
 drop_stats
------------
(1 row)
```

5. 데이터베이스의 위반 쿼리를 모두 삭제합니다.

이 삭제는 백업을 복원하는 데이터베이스의 기존 쿼리를 제거합니다. 이 쿼리는 기존 쿼리를 표시합니다.

```sql
edb=# SELECT * FROM sqlprotect.edb_sql_protect_queries;
```

출력

```text
 username  | ip_address | port | machine_name | date_time | query
-----------+------------+------+--------------+-----------+-------
(0 rows)
```

앞의 쿼리에 나타나는 각 행에 대해, 항목의 역할 이름을 지정하여 `drop_queries` 함수를 사용합니다. 예를 들어 `username` 컬럼에 `appuser`가 있는 행이 나타나면 다음 명령을 발행하여 제거합니다.

```sql
edb=# SELECT sqlprotect.drop_queries('appuser');
```

출력

```text
 drop_queries
--------------
(1 row)
```

6. 원본 데이터베이스에서 SQL/Protect로 보호되었던 역할 이름이 새 데이터베이스가 있는 데이터베이스 서버에 있는지 확인합니다.

원본 데이터베이스와 새 데이터베이스가 동일한 데이터베이스 서버에 있고, 데이터베이스 서버에서 이 역할들을 삭제하지 않았다면 아무것도 할 필요가 없습니다.

7. `import_sqlprotect('sqlprotect_file')` 함수를 실행합니다. 여기서 `sqlprotect_file`은 위 "데이터베이스 백업"의 2단계에서 생성한 파일의 전체 한정 경로입니다.

```sql
newdb=# SELECT sqlprotect.import_sqlprotect('/tmp/sqlprotect.dmp');
```

출력

```text
 import_sqlprotect
-------------------
(1 row)
```

`edb_sql_protect`와 `edb_sql_protect_rel` 테이블에는 새 데이터베이스에서 할당된 데이터베이스 객체의 OID를 포함하는 항목이 채워집니다. `edb_sql_protect_stats` 통계 뷰에도 원본 데이터베이스에서 가져온 통계가 표시됩니다.

이 데이터베이스에 대해 SQL/Protect 테이블과 통계가 올바르게 복원됩니다. 다음 EDB Postgres Advanced Server 시스템 카탈로그 쿼리로 확인합니다.

```sql
newdb=# SELECT datname, oid FROM pg_database;
```

출력

```text

-----------+-------
 template1 |     1
 template0 | 13909
 edb       | 13917
 newdb     | 16679
(4 rows)
```

```sql
newdb=# SELECT rolname, oid FROM pg_roles;
```

```text

--------------+-------

 newuser      | 16678
(3 rows)
```

```sql
newdb=# SELECT relname, oid FROM pg_class WHERE relname IN
('dept','emp','appuser_tab');
```

`edb_sql_protect`와 `edb_sql_protect_rel` 테이블의 컬럼에 대해 다음을 유의하십시오.

- **dbid.** `newdb`에 대한 `pg_database`의 `oid` 컬럼 값과 일치합니다.

- **roleid.** `appuser`에 대한 `pg_roles`의 `oid` 컬럼 값과 일치합니다.

또한 `edb_sql_protect_rel` 테이블에서 `relid` 컬럼의 값은 릴레이션 `dept`와 `appuser_tab`에 대한 `pg_class`의 `oid` 컬럼 값과 일치합니다.

8. 새 데이터베이스를 실행하는 데이터베이스 서버의 `postgresql.conf` 파일에서 SQL/Protect 구성 파라미터가 원하는 대로 설정되어 있는지 확인합니다. 적절히 데이터베이스 서버를 재시작하거나 구성 파일을 다시 로드합니다.

이제 SQL/Protect를 사용하여 데이터베이스를 모니터링할 수 있습니다.
