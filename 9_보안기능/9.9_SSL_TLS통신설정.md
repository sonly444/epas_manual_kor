# SSL/TLS 통신 설정 — EPAS 18 Security

## 개요

EDB Postgres Advanced Server는 클라이언트와 서버 간 통신을 암호화하기 위해 SSL 연결을 사용하는 기능을 기본(native)으로 지원합니다. 이 기능을 사용하려면 클라이언트와 서버 양쪽 시스템에 OpenSSL이 설치되어 있어야 합니다.

현재 실제로 사용되는 프로토콜은 TLS이지만, PostgreSQL 및 EPAS의 설정 이름과 문서에서는 관례적으로 SSL이라는 용어를 사용합니다. 이 문서에서도 SSL과 TLS를 같은 의미로 사용합니다.

## 기본 설정 (Basic Setup)

SSL 지원이 포함된 상태에서 `postgresql.conf` 파일의 `ssl` 파라미터를 `on`으로 설정하면 서버가 TLS 프로토콜을 사용하는 암호화 연결을 지원합니다.

```ini
ssl = on
```

서버는 동일한 TCP 포트에서 일반 연결과 SSL 연결을 모두 대기하며, 접속하는 클라이언트가 SSL 사용 여부를 선택합니다. 일부 또는 모든 연결에 SSL 사용을 강제하려면 [암호화 통신 강제](#암호화-통신-강제)를 참고하십시오.

SSL 모드로 시작하려면 서버 인증서와 개인키 파일이 필요합니다. 기본적으로 두 파일은 서버 데이터 디렉터리에 각각 `server.crt`와 `server.key`라는 이름으로 저장합니다. 다른 이름이나 위치를 사용하려면 `ssl_cert_file`과 `ssl_key_file` 파라미터를 설정합니다.

Unix 시스템에서 `server.key`는 다른 사용자가 읽을 수 없도록 권한을 제한해야 합니다.

```bash
chmod 0600 server.key
```

또는 파일을 `root`가 소유하고 데이터베이스 서버 계정이 속한 그룹에 읽기 권한을 부여하도록 `0640`으로 설정할 수 있습니다.

개인키가 암호로 보호되어 있으면 서버는 시작 과정에서 암호를 입력받아야 합니다. 무인 시작이나 재시작이 필요한 환경에서는 `ssl_passphrase_command`와 `ssl_passphrase_command_supports_reload` 설정을 검토하십시오.

`server.crt`의 첫 번째 인증서는 서버 개인키와 일치하는 서버 인증서여야 합니다. 필요한 중간 인증서는 같은 파일 뒤에 추가할 수 있지만, 루트 인증서는 일반적으로 `server.crt`에 포함하지 않습니다.

## 인증서 생성 (Creating Certificates)

시험용으로 365일 동안 유효한 자체 서명 인증서를 생성하려면 `dbhost.yourdomain.com`을 실제 서버 호스트 이름으로 바꾸어 다음 명령을 실행합니다.

```bash
openssl req -new -x509 -days 365 -nodes -text -out server.crt \
  -keyout server.key -subj "/CN=dbhost.yourdomain.com"
chmod og-rwx server.key
```

자체 서명 인증서는 시험에 사용할 수 있지만, 운영 환경에서는 신뢰할 수 있는 인증기관(CA)이 서명한 인증서를 사용해야 합니다. CA를 구성하려면 먼저 CA의 CSR과 개인키를 생성합니다.

```bash
openssl req -new -nodes -text -out root.csr \
  -keyout root.key -subj "/CN=root.yourdomain.com"
chmod og-rwx root.key

openssl x509 -req -in root.csr -text -days 3650 \
  -extfile /etc/ssl/openssl.cnf -extensions v3_ca \
  -signkey root.key -out root.crt
```

이어서 CA가 서명한 서버 인증서를 생성합니다.

```bash
openssl req -new -nodes -text -out server.csr \
  -keyout server.key -subj "/CN=dbhost.yourdomain.com"
chmod og-rwx server.key

openssl x509 -req -in server.csr -text -days 365 \
  -CA root.crt -CAkey root.key -CAcreateserial \
  -out server.crt
```

`server.crt`와 `server.key`는 서버에 저장하고, `root.crt`는 클라이언트가 서버 인증서의 신뢰 체인을 검증할 수 있도록 클라이언트에 배포합니다. `root.key`는 향후 인증서 발급에 사용하므로 안전한 오프라인 위치에 보관해야 합니다.

> 참고: 데이터베이스 함수 `openssl_rsa_generate_key`, `openssl_rsa_key_to_csr`, `openssl_csr_to_crt`, `openssl_rsa_generate_crl`을 이용하는 방법은 별첨 **SSL/TLS 통신 설정 기능 테스트 결과 및 재현 절차**를 참고하십시오. `sslutils` 1.4.1에서는 인증서 및 개인키 경로 인수가 데이터 디렉터리(`PGDATA`) 내부에 있어야 합니다.

## 클라이언트 인증서 사용 (Using Client Certificates)

클라이언트가 신뢰할 수 있는 인증서를 제시하도록 요구하려면, 신뢰하는 CA 인증서를 서버 데이터 디렉터리에 저장하고 `postgresql.conf`의 `ssl_ca_file` 파라미터를 설정합니다. 그다음 `pg_hba.conf`의 해당 `hostssl` 레코드에 `clientcert=verify-ca` 또는 `clientcert=verify-full` 옵션을 추가합니다.

- `clientcert=verify-ca`: 클라이언트 인증서가 신뢰하는 CA 중 하나에 의해 서명되었는지 검증합니다.
- `clientcert=verify-full`: 인증서 체인을 검증하고 인증서의 CN이 접속 사용자 이름 또는 사용자 매핑과 일치하는지 확인합니다.

인증서 폐기 목록은 `ssl_crl_file` 또는 `ssl_crl_dir` 파라미터를 설정한 경우 함께 검사됩니다. `clientcert` 옵션은 `hostssl` 레코드에서만 사용할 수 있습니다.

## 암호화 통신 강제

클라이언트 인증 방식은 `pg_hba.conf` 파일로 제어합니다. TCP/IP 연결 레코드에는 다음 유형을 사용할 수 있습니다.

- `host`: SSL 및 비SSL 연결 모두 일치합니다.
- `hostssl`: SSL로 암호화된 연결만 일치합니다. 서버가 SSL을 지원하고 `ssl=on`이어야 합니다.
- `hostnossl`: SSL을 사용하지 않는 연결만 일치합니다.

암호화 통신을 강제하려면 허용할 연결에 `hostssl`을 사용하고, 비SSL 연결을 `hostnossl` 레코드로 명시적으로 거부합니다. `pg_hba.conf`는 위에서 아래 순서로 검사하므로 더 넓은 범위의 `host` 레코드가 앞에 있지 않은지 확인해야 합니다.

```text
# TYPE      DATABASE  USER  ADDRESS        METHOD
hostssl     all       all   0.0.0.0/0      scram-sha-256
hostnossl   all       all   0.0.0.0/0      reject
```

클라이언트 인증서 자체를 인증 수단으로 사용하려면 `cert` 방식을 지정할 수 있습니다. 인증서의 CN은 사용자 이름 또는 사용자 매핑과 대응되어야 합니다.

```text
# TYPE      DATABASE  USER  ADDRESS        METHOD
hostssl     all       all   0.0.0.0/0      cert
```

기존 비밀번호 인증과 클라이언트 인증서 검증을 함께 사용하려면 `clientcert` 옵션을 지정합니다.

```text
# TYPE      DATABASE  USER  ADDRESS        METHOD          OPTIONS
hostssl     all       all   0.0.0.0/0      scram-sha-256   clientcert=verify-full
```

`pg_hba.conf`를 변경한 후 서버에 SIGHUP 신호를 보내거나 다음 함수를 실행하여 설정을 다시 읽습니다.

```sql
SELECT pg_reload_conf();
```

> 참고: 기존 loopback 규칙이 `ident`인 환경에서는 `psql -h 127.0.0.1` 시험이 SSL 협상 이후 인증 단계에서 실패할 수 있습니다. 시험용 HBA 규칙, SSL/비SSL 비교 명령과 복원 절차는 별첨 기능 테스트 문서를 참고하십시오.

## SSL 서버 파일 (SSL Server File Usage)

다음 표는 서버 SSL 설정과 관련된 주요 파일을 설명합니다. 파일 이름은 기본값이며 로컬 구성에 따라 다를 수 있습니다.

| 파일(파라미터) | 내용 | 효과 |
|---|---|---|
| `ssl_cert_file` (`$PGDATA/server.crt`) | 서버 인증서 | 클라이언트에 서버 신원을 제시 |
| `ssl_key_file` (`$PGDATA/server.key`) | 서버 개인키 | 서버가 인증서의 개인키를 보유하고 있음을 증명 |
| `ssl_ca_file` | 신뢰하는 CA 인증서 | 클라이언트 인증서의 서명 체인 검증 |
| `ssl_crl_file` | CA의 인증서 폐기 목록 | 폐기된 클라이언트 인증서 거부 |
| `ssl_crl_dir` | CRL 디렉터리 | 여러 CRL 파일 관리 |

서버는 시작할 때와 SSL 구성을 다시 읽을 때 이 파일들을 읽습니다. 시작 과정에서 파일 오류가 발견되면 서버 시작이 거부될 수 있습니다. 설정 재로드 중 오류가 발생하면 새 파일을 적용하지 않고 기존 SSL 구성을 계속 사용하므로 서버 로그를 확인해야 합니다.

## 주요 SSL 구성 파라미터 (postgresql.conf)

| 파라미터 | 설명 |
|---|---|
| `ssl` | SSL 연결 활성화 여부(`on`/`off`) |
| `ssl_cert_file` | 서버 인증서 파일 경로 |
| `ssl_key_file` | 서버 개인키 파일 경로 |
| `ssl_ca_file` | 클라이언트 인증서 검증에 사용할 CA 인증서 파일 |
| `ssl_crl_file` / `ssl_crl_dir` | 인증서 폐기 목록 파일 또는 디렉터리 |
| `ssl_ciphers` | TLS 1.2 이하에서 사용할 암호군 목록 |
| `ssl_ciphersuites` | TLS 1.3에서 사용할 암호군 목록 |
| `ssl_min_protocol_version` | 허용할 최소 TLS 프로토콜 버전. 기본값은 `TLSv1.2` |
| `ssl_max_protocol_version` | 허용할 최대 TLS 프로토콜 버전. 빈 값이면 제한 없음 |
| `ssl_passphrase_command` | 암호화된 개인키의 암호를 얻기 위해 실행할 외부 명령 |
| `ssl_passphrase_command_supports_reload` | 설정 재로드 시 passphrase 명령 사용 가능 여부 |

> 참고: 인증만 수행하고 통신 내용을 암호화하지 않는 NULL 암호군은 중간자 공격자가 통신을 읽을 수 있으므로 권장하지 않습니다.
