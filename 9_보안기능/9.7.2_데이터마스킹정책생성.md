> 상위: # 데이터 마스킹 (Data Redaction) — EPAS 18 Security

## 2. 데이터 마스킹 정책 생성 (Creating a data redaction policy)

> 원문: [creating_a_data_redaction_policy](https://www.enterprisedb.com/docs/epas/latest/epas_security_guide/05_data_redaction/creating_a_data_redaction_policy/)

`CREATE REDACTION POLICY` 명령은 테이블에 대한 새 데이터 마스킹 정책을 정의합니다.

### 구문 (Synopsis)
```sql
CREATE REDACTION POLICY <name> ON <table_name>
  [ FOR ( <expression> ) ]
  [ ADD [ COLUMN ] <column_name> USING <funcname_clause>
    [ WITH OPTIONS ( [ <redaction_option> ]
      [, <redaction_option> ] )
    ]
  ] [, ...]
```
여기서 `redaction_option`은:
```sql
{ SCOPE <scope_value> |
  EXCEPTION <exception_value> }
```

### 설명
이 명령은 "마스킹 함수를 사용하여 컬럼 데이터를 마스킹함으로써 테이블에 대한 새 컬럼 수준 보안 정책"을 수립합니다. 새로 생성된 마스킹 정책은 기본적으로 활성화됩니다. `ALTER REDACTION POLICY ... DISABLE`로 비활성화할 수 있습니다.

- `FOR ( expression )`: 마스킹 정책 표현식을 추가하는 형태.
- `ADD [ COLUMN ]`: 테이블의 컬럼을 마스킹 정책에 추가하는 선택적 형태. `USING` 절은 마스킹 함수 표현식을 지정합니다. 여러 컬럼을 추가하려면 `ADD [ COLUMN ]` 형태를 여러 번 사용할 수 있습니다. 선택적 `WITH OPTIONS ( ... )` 절은 적용할 scope 또는 exception을 지정합니다. 지정하지 않으면 scope 기본값은 `query`, exception 기본값은 `none`입니다.

### 파라미터
- `name`: 생성할 마스킹 정책 이름. 해당 테이블의 다른 기존 정책 이름과 구별되어야 함.
- `table_name`: 정책이 적용되는 테이블의 (선택적 스키마 한정) 이름.
- `expression`: 마스킹 정책 표현식. 이 표현식이 false로 평가되면 마스킹이 적용되지 않음.
- `column_name`: 정책을 생성하는 테이블의 기존 컬럼 이름.
- `funcname_clause`: 마스킹된 컬럼 값 계산 방법을 결정하는 마스킹 함수. 반환 타입은 정책을 추가하는 컬럼 타입과 동일해야 함.
- `scope_value`: 컬럼에 마스킹을 적용할 쿼리 부분을 식별. 값은 `query`, `top_tlist`, `top_tlist_or_error`. `query`이면 쿼리 내 위치와 무관하게 컬럼에 마스킹 적용. `top_tlist`이면 쿼리의 최상위 대상 목록(top target list)에 나타날 때만 적용. `top_tlist_or_error`이면 `top_tlist`와 동일하나 컬럼이 쿼리의 다른 곳에 나타나면 오류 발생.
- `exception_value`: 마스킹이 면제되는 쿼리 부분을 식별. 값은 `none`, `equal`, `leakproof`. `none`이면 면제 없음. `equal`이면 동등성 테스트에 사용될 때 컬럼이 마스킹되지 않음. `leakproof`이면 leakproof 함수가 적용될 때 마스킹되지 않음.

### 참고
- 테이블에 마스킹 정책을 생성·변경하려면 그 테이블의 소유자여야 합니다.
- 슈퍼유저와 테이블 소유자는 마스킹 정책에서 면제됩니다.

### 예제
`employees` 테이블에 대한 마스킹 정책 구성 요소 생성:
```sql
CREATE TABLE employees (
 id          integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
 name        varchar(40) NOT NULL,
 ssn         varchar(11) NOT NULL,
 phone       varchar(10),
 birthday    date,
 salary      money,
 email       varchar(100)
);

INSERT INTO employees (name, ssn, phone, birthday, salary, email)
VALUES
( 'Sally Sample', '020-78-9345', '5081234567', '1961-02-02', 51234.34,
'sally.sample@enterprisedb.com'),
( 'Jane Doe', '123-33-9345', '6171234567', '1963-02-14', 62500.00,
'jane.doe@gmail.com'),
( 'Bill Foo', '123-89-9345', '9781234567','1963-02-14', 45350,
'william.foe@hotmail.com');

CREATE USER hr;
CREATE USER alice;
GRANT ALL ON employees TO hr, alice;

CREATE OR REPLACE FUNCTION redact_ssn (ssn varchar(11)) RETURN varchar(11) IS
BEGIN
   /* replaces 020-12-9876 with xxx-xx-9876 */
   return overlay (ssn placing 'xxx-xx' from 1) ;
END;

CREATE OR REPLACE FUNCTION redact_salary () RETURN money IS BEGIN return
0::money;
END;
```
`ssn`·`salary` 컬럼을 기본 scope·exception으로 마스킹하되, `ssn`은 동등성 조건에서 접근 가능하게 하고 `hr` 사용자는 면제하는 정책 생성:
```sql
CREATE REDACTION POLICY redact_policy_personal_info ON employees FOR (session_user != 'hr')
ADD COLUMN ssn USING redact_ssn(ssn) WITH OPTIONS (SCOPE query, EXCEPTION equal),
ADD COLUMN salary USING redact_salary();
```
`hr` 사용자는 모든 컬럼 데이터를 볼 수 있고(원본 SSN·급여 표시), 일반 사용자 `alice`는 `ssn`이 `xxx-xx-9345`로, `salary`가 `$0.00`으로 마스킹되어 표시됩니다. 다만 `exception_value` 설정 덕분에 `ssn`은 동등성 검사에 사용할 때 접근 가능합니다:
```sql
edb=> SELECT * FROM employees WHERE substring(ssn from 0 for 4) = '123';
```
(Jane Doe·Bill Foo 두 행 반환, 표시값은 여전히 `xxx-xx-9345`)

### 주의 사항 (Caveats)
- 상속 계층(inheritance hierarchy)에 생성된 마스킹 정책은 계단식으로 전파되지 않습니다. 부모에 정책을 만들어도 이를 상속하는 자식 테이블에는 적용되지 않으며 그 반대도 마찬가지입니다. 자식 테이블에 접근 권한이 있는 사용자는 마스킹되지 않은 데이터를 볼 수 있습니다.
- 슈퍼유저나 테이블 소유자가 테이블에 구체화 뷰를 만들고 비슈퍼유저에게 테이블·구체화 뷰에 대한 `GRANT SELECT`를 부여하면, 비슈퍼유저가 구체화 뷰를 통해 마스킹되지 않은 데이터에 접근할 수 있습니다.
- 마스킹 함수 본문에서 접근하는 객체는 스키마 한정되어야 합니다. 그렇지 않으면 `pg_dump`가 실패할 수 있습니다.

### 호환성
`CREATE REDACTION POLICY`는 EDB 확장입니다.
