# SQL/Protect 개요 (SQL/Protect overview) — EPAS 18

> 원문: [EPAS v18 — Security guide › Protecting against SQL injection attacks › SQL/Protect overview](https://www.enterprisedb.com/docs/epas/latest/epas_security_guide/02_protecting_against_sql_injection_attacks/01_sql_protect_overview/)
> EPAS v18 공식 문서의 한글 **전문 번역**입니다. 기능명·뷰·컬럼·코드는 원문 그대로 보존했습니다.

SQL/Protect는 여러 유형의 SQL 인젝션 공격을 방어합니다.

## SQL 인젝션 공격의 유형 (Types of SQL injection attacks)

SQL 인젝션 공격을 수행하는 데는 여러 가지 기법이 사용됩니다. 각 기법은 특정 *시그니처(signature)*로 특징지어집니다. SQL/Protect는 다음 시그니처에 대해 쿼리를 검사합니다.

### 인가되지 않은 릴레이션 (Unauthorized relations)

EDB Postgres Advanced Server는 관리자가 릴레이션(테이블, 뷰 등)에 대한 접근을 제한할 수 있게 하지만, 많은 관리자가 이 번거로운 작업을 수행하지 않습니다. SQL/Protect는 사용자가 접근하는 릴레이션을 추적하는 *학습(learn)* 모드를 제공합니다.

이 모드를 통해 관리자는 애플리케이션의 작업 부하를 검토할 수 있고, SQL/Protect는 특정 사용자 또는 역할의 사용자 그룹에 대해 애플리케이션이 접근할 수 있는 릴레이션을 학습할 수 있습니다.

SQL/Protect가 *수동(passive)* 또는 *능동(active)* 모드로 전환되면, 들어오는 쿼리는 학습된 릴레이션 목록과 대조하여 확인됩니다.

### 유틸리티 명령 (Utility commands)

SQL 인젝션 공격에 흔히 사용되는 기법은 유틸리티 명령을 실행하는 것으로, 이는 일반적으로 SQL 데이터 정의 언어(DDL) 구문입니다. 예로는 다른 시스템 리소스에 접근할 수 있는 사용자 정의 함수를 생성하는 것이 있습니다.

SQL/Protect는 표준 애플리케이션 처리 중에 일반적으로 필요하지 않은 모든 유틸리티 명령의 실행을 차단할 수 있습니다.

### SQL 항진명제 (SQL tautology)

SQL 인젝션 공격에 가장 자주 사용되는 기법은 항진명제적(tautological) `WHERE` 절 조건(즉, 항상 참인 조건)을 발행하는 것입니다.

다음은 그 예입니다.

`WHERE password = 'x' OR 'x'='x'`

공격자는 대개 이 기법을 사용하여 보안 취약점을 식별하기 시작합니다. SQL/Protect는 항진명제적 조건 절을 사용하는 쿼리를 차단할 수 있습니다.

### 무한정 DML 구문 (Unbounded DML statements)

SQL 인젝션 공격 중에 취해지는 위험한 행동은 무한정(unbounded) DML 구문을 실행하는 것입니다. 이는 `WHERE` 절이 없는 `UPDATE` 및 `DELETE` 구문입니다. 예를 들어 공격자가 모든 사용자의 비밀번호를 알려진 값으로 업데이트하거나, 핵심 테이블의 모든 데이터를 삭제하여 서비스 거부(denial of service) 공격을 시작할 수 있습니다.

## SQL 인젝션 공격 모니터링 (Monitoring SQL injection attacks)

SQL/Protect는 SQL 인젝션 공격을 모니터링하고 보고할 수 있습니다.

### 보호된 역할 (Protected roles)

SQL 인젝션 공격 모니터링에는, 세션의 현재 사용자가 *보호된 역할(protected role)*인 데이터베이스 세션에서 발생하는 SQL 구문을 분석하는 것이 포함됩니다. 보호된 역할은 데이터베이스 관리자가 SQL/Protect를 사용하여 모니터링하기로 선택한 EDB Postgres Advanced Server 사용자 또는 그룹입니다. (EDB Postgres Advanced Server에서 사용자와 그룹을 통칭하여 *역할(role)*이라고 합니다.)

각 보호된 역할을 모니터링 대상 SQL 인젝션 공격 유형별로 사용자 지정할 수 있습니다. 이 접근 방식은 역할별로 다른 수준의 보호를 제공하며 DBA의 사용자 유지 관리 부담을 크게 줄여줍니다.

슈퍼유저 권한을 가진 역할은 보호된 역할로 만들 수 없습니다. 보호된 비슈퍼유저 역할이 나중에 슈퍼유저가 되면, 그 슈퍼유저가 명령을 발행하려고 할 때 특정 동작이 발생합니다.

- SQL/Protect는 보호된 슈퍼유저가 발행하는 모든 명령에 대해 경고 메시지를 발행합니다.
- `edb_sql_protect_stats`의 superusers 컬럼 통계가 보호된 슈퍼유저가 발행하는 모든 명령마다 증가합니다. `edb_sql_protect_stats` 뷰에 대한 정보는 아래 "공격 시도 통계"를 참고하십시오.
- 능동(active) 모드의 SQL/Protect는 보호된 슈퍼유저가 발행한 모든 명령의 실행을 방지합니다.

슈퍼유저 권한을 가진 보호된 역할이 더 이상 슈퍼유저가 아니도록 변경하거나, 보호되지 않은 역할로 되돌리십시오.

### 공격 시도 통계 (Attack attempt statistics)

SQL/Protect는 보호된 역할이 공격으로 간주되는 명령을 사용할 때마다 이를 기록합니다. 위 "SQL 인젝션 공격의 유형"에서 설명한 대로 SQL 인젝션 공격 유형별로 통계를 수집합니다.

이 통계는 `edb_sql_protect_stats` 뷰에서 접근할 수 있습니다. 이 뷰를 쉽게 모니터링하여 잠재적 공격의 시작을 식별할 수 있습니다.

`edb_sql_protect_stats`의 컬럼은 다음을 모니터링합니다.

- **username.** 보호된 역할의 이름.
- **superusers.** 보호된 역할이 슈퍼유저일 때 발행된 SQL 구문의 수. 사실상 보호된 슈퍼유저가 발행하는 모든 SQL 구문이 이 통계를 증가시킵니다. 보호된 슈퍼유저에 대한 정보는 위 "보호된 역할"을 참고하십시오.
- **relations.** 보호된 역할이 학습하지 않은 릴레이션을 참조하며 발행한 SQL 구문의 수. (이러한 릴레이션은 역할의 보호된 릴레이션 목록에 없습니다.)
- **commands.** 보호된 역할이 발행한 DDL 구문의 수.
- **tautology.** 보호된 역할이 발행한, 항진명제적 조건을 포함한 SQL 구문의 수.
- **dml.** 보호된 역할이 발행한, `WHERE` 절을 포함하지 않은 `UPDATE` 및 `DELETE` 구문의 수.

이 통계는 데이터베이스 관리자가 귀중한 데이터의 도난이나 기타 악의적 행위를 사전에 예방적으로 대응할 기회를 제공합니다.

역할이 둘 이상의 데이터베이스에서 보호되는 경우, 각 데이터베이스에서의 공격에 대한 역할 통계는 별도로 유지되며 해당 데이터베이스에 연결된 경우에만 볼 수 있습니다.

> **참고**
> SQL/Protect 통계는 데이터베이스 서버가 실행 중인 동안 메모리에 유지됩니다. 데이터베이스 서버가 종료되면 통계는 EDB Postgres Advanced Server 홈 디렉터리의 `data/global` 하위 디렉터리에 `edb_sqlprotect.stat`이라는 바이너리 파일로 저장됩니다.

### 공격 시도 쿼리 (Attack attempt queries)

SQL/Protect가 공격으로 간주하는, 보호된 역할의 명령 사용은 각각 `edb_sql_protect_queries` 뷰에 기록되며, 이 뷰에는 다음 컬럼이 포함됩니다.

- **username.** 데이터베이스 서버에 로그인하는 데 사용된 공격자의 데이터베이스 사용자 이름.
- **ip_address.** 공격이 시작된 머신의 IP 주소.
- **port.** 공격이 발생한 포트 번호.
- **machine_name.** 알려진 경우, 공격이 발생한 머신의 이름.
- **date_time.** 데이터베이스 서버가 쿼리를 수신한 날짜와 시간. 시간은 분 단위 정밀도로 저장됩니다.
- **query.** 공격자가 보낸 쿼리 문자열.

`edb_sql_protect_queries`에 저장되는 위반 쿼리의 최대 수는 `edb_sql_protect.max_queries_to_save` 구성 파라미터로 제어됩니다.

역할이 둘 이상의 데이터베이스에서 보호되는 경우, 각 데이터베이스에서의 공격에 대한 역할 쿼리는 별도로 유지됩니다. 이는 해당 데이터베이스에 연결된 경우에만 볼 수 있습니다.
