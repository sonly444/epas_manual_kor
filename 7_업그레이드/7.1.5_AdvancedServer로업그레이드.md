## 4.2 EDB Postgres Advanced Server로 업그레이드 (Upgrading to EDB Postgres Advanced Server)

> 원문: [03_upgrading_to_advanced_server](https://www.enterprisedb.com/docs/epas/latest/upgrading/major_upgrade/03_upgrading_to_advanced_server/)
> EPAS v18 공식 문서의 한글 **전문 번역**입니다. 명령·경로·서비스명·플래그·파일 이름은 원문 그대로 보존했습니다.

`pg_upgrade`를 사용하여 기존 EDB Postgres Advanced Server 설치에서, EDB Postgres Advanced Server 인스톨러가 빌드한 클러스터 또는 `initdb` 명령으로 생성한 대체 클러스터로 업그레이드할 수 있습니다.

`initdb` 명령으로 생성한 빈 클러스터로 업그레이드하는 기본 단계는, EDB Postgres Advanced Server 인스톨러가 생성한 클러스터로 업그레이드하는 단계와 동일합니다. 다만 2단계(edb 데이터베이스 비우기)를 생략하고, 업그레이드 대상 클러스터를 지정할 때 대체 클러스터의 위치를 대신 지정하면 됩니다.

업그레이드 과정에서 문제가 발생하면 이전 버전으로 되돌릴 수 있습니다. 이 과정에 대한 자세한 내용은 [이전 클러스터로 되돌리기(Reverting to the old cluster)](https://www.enterprisedb.com/docs/epas/latest/upgrading/major_upgrade/06_reverting_to_the_old_cluster/#reverting_to_the_old_cluster)를 참고하십시오.

EDB Postgres Advanced Server 업그레이드를 수행하려면 운영체제 슈퍼유저 또는 Windows 관리자(Administrator)여야 합니다.

## 1단계 — 새 서버 설치 (Step 1 - Install the new server)

새 버전의 EDB Postgres Advanced Server를 설치하되, 이전 EDB Postgres Advanced Server 설치 시 설치했던 것과 동일한 비서버(non-server) 구성 요소를 지정합니다. 새 클러스터와 이전 클러스터는 서로 다른 디렉터리에 있어야 합니다.

## 2단계 — 대상 데이터베이스 비우기 (Step 2 - Empty the target database)

대상 클러스터에는 데이터가 없어야 합니다. `initdb` 명령으로 빈 클러스터를 생성하거나, EDB Postgres Advanced Server 설치 중에 생성된 데이터베이스를 비울 수 있습니다. EDB Postgres Advanced Server를 PostgreSQL 모드로 설치한 경우 인스톨러는 `postgres`라는 단일 데이터베이스를 생성합니다. EDB Postgres Advanced Server를 Oracle 모드로 설치한 경우 `postgres` 데이터베이스와 `edb` 데이터베이스를 생성합니다.

대상 데이터베이스를 비우는 가장 쉬운 방법은 데이터베이스를 드롭한 뒤 새 데이터베이스를 생성하는 것입니다. `DROP DATABASE` 명령을 호출하기 전에, 현재 해당 데이터베이스를 사용 중인 모든 사용자의 연결을 끊고 실행 중인 서비스를 중지해야 합니다.

Windows에서는 제어판(Control Panel)에서 Services 관리자로 이동합니다. **Services** 목록에서 각 서비스를 선택하고 **Stop**을 선택합니다.

현재 EDB Postgres Advanced Server에 연결된 서비스를 중지한 후, EDB-PSQL 명령줄 클라이언트를 사용하여 데이터베이스를 드롭하고 생성할 수 있습니다. 클라이언트가 열리면 데이터베이스 슈퍼유저로 `template1` 데이터베이스에 접속합니다. 인증 정보를 요구하면 입력합니다. 그런 다음 아래 명령으로 데이터베이스를 드롭합니다.

```sql
DROP DATABASE <database_name>;
```

여기서 `database_name`은 데이터베이스의 이름입니다.

그런 다음 `template1` 데이터베이스의 내용을 기반으로 빈 데이터베이스를 생성합니다.

```sql
CREATE DATABASE <database_name>;
```

## 3단계 — 두 서버를 trust 모드로 설정 (Step 3 - Set both servers in trust mode)

업그레이드 과정에서 `pg_upgrade`는 이전 서버와 새 서버에 여러 번 접속합니다. 접속 과정을 단순화하기 위해 `pg_hba.conf` 파일을 편집하여 인증 모드를 `trust`로 설정할 수 있습니다. `pg_hba.conf` 파일을 수정하려면 시작 메뉴에서 **EDB Postgres > EDB Postgres Advanced Server > Expert Configuration**을 선택합니다. **Edit pg_hba.conf**를 선택하여 `pg_hba.conf` 파일을 엽니다.

이전 EDB Postgres Advanced Server 설치와 새 EDB Postgres Advanced Server 서버 모두에 대해 trust 인증을 허용해야 합니다. 그림과 같이 두 EDB Postgres Advanced Server 설치의 `pg_hba.conf` 파일을 편집합니다.

![trust 인증을 사용하도록 EDB Postgres Advanced Server 구성](https://www.enterprisedb.com/docs/static/7f1351cf16dcf4df13fd460b5afc1079/889a4/configuring_advanced_server_to_use_trust_authentication.png)

각 파일을 편집한 후 파일을 저장하고 편집기를 종료합니다.

업그레이드 과정에서 시스템이 `md5` 인증 모드를 유지해야 하는 경우, 비밀번호 파일(Windows에서는 `pgpass.conf`, Linux에서는 `.pgpass`)에 데이터베이스 슈퍼유저의 사용자 비밀번호를 지정할 수 있습니다. 비밀번호 파일 구성에 대한 자세한 내용은 [PostgreSQL 코어 문서](https://www.postgresql.org/docs/current/static/libpq-pgpass.html)를 참고하십시오.

## 4단계 — 모든 구성 요소 서비스와 서버 중지 (Step 4 - Stop all component services and servers)

## 5단계(Linux 전용) — 클러스터 소유자 신원 가정 (Step 5 for Linux only)

Linux를 사용하는 경우, EDB Postgres Advanced Server 클러스터 소유자의 신원을 가정합니다. 이 예에서는 EDB Postgres Advanced Server가 기본값인 Oracle 호환 데이터베이스 모드로 설치되어 `enterprisedb`가 클러스터 소유자로 할당되었다고 가정합니다. (PostgreSQL 호환 데이터베이스 모드로 설치한 경우에는 `postgres`가 클러스터 소유자입니다.)

```shell
su - enterprisedb
```

요청되면 EDB Postgres Advanced Server 클러스터 소유자 비밀번호를 입력합니다. 그런 다음 `pg_upgrade` 실행 파일의 위치를 포함하도록 경로를 설정합니다.

```shell
export PATH=$PATH:/usr/edb/as18/bin
```

업그레이드 과정에서 `pg_upgrade`는 `enterprisedb` 사용자의 현재 작업 디렉터리에 파일을 씁니다. `enterprisedb` 사용자가 쓰기 권한을 가진 디렉터리에서 `pg_upgrade`를 호출해야 합니다. 위 명령을 수행한 후, `enterprisedb` 사용자가 파일을 쓸 수 있는 충분한 권한을 가진 디렉터리로 이동합니다.

```shell
cd /tmp
```

## 5단계(Windows 전용) — 클러스터 소유자 신원 가정 (Step 5 for Windows only)

Windows를 사용하는 경우, 터미널 창을 열고 EDB Postgres Advanced Server 클러스터 소유자의 신원을 가정한 뒤 `pg_upgrade` 실행 파일에 대한 경로를 설정합니다.

EDB Postgres Advanced Server 최초 설치 시 `--serviceaccount service_account_user` 파라미터를 지정했다면, `service_account_user`가 EDB Postgres Advanced Server 클러스터 소유자입니다. 이 경우 `RUNAS` 명령으로 이 사용자 권한을 부여합니다.

```sql
RUNAS /USER:service_account_user "CMD.EXE"
SET PATH=%PATH%;C:\Program Files\edb\as18\bin
```

업그레이드 과정에서 `pg_upgrade`는 서비스 계정 사용자의 현재 작업 디렉터리에 파일을 씁니다. 서비스 계정 사용자가 쓰기 권한을 가진 디렉터리에서 `pg_upgrade`를 호출해야 합니다. 위 명령을 수행한 후, 서비스 계정 사용자가 파일을 쓸 권한이 있는 디렉터리로 이동합니다.

```shell
cd %TEMP%
```

EDB Postgres Advanced Server 최초 설치 시 `--serviceaccount` 파라미터를 생략했다면, EDB Postgres Advanced Server 서비스와 데이터베이스 클러스터의 기본 소유자는 `NT AUTHORITY\NetworkService`입니다.

`NT AUTHORITY\NetworkService`가 서비스 계정 사용자인 경우, `RUNAS` 명령을 사용하지 못할 수 있습니다. `RUNAS`는 비밀번호를 요구하지만 `NT AUTHORITY\NetworkService` 계정에는 비밀번호가 할당되어 있지 않기 때문입니다. 따라서 일반적으로 "Unable to acquire user password."와 같은 오류 메시지와 함께 실패합니다.

이런 상황에서는 Windows 유틸리티 프로그램 `PsExec`를 사용하여 `CMD.EXE`를 서비스 계정 `NT AUTHORITY\NetworkService`로 실행해야 합니다.

`PsExec` 프로그램은 [Microsoft 사이트](https://technet.microsoft.com/en-us/sysinternals/bb897553.aspx)에서 제공하는 `PsTools`를 다운로드하여 얻을 수 있습니다.

그런 다음 아래 명령으로 `CMD.EXE`를 `NT AUTHORITY\NetworkService`로 실행할 수 있습니다. 이어서 `pg_upgrade` 실행 파일에 대한 경로를 설정합니다.

```shell
psexec.exe -u "NT AUTHORITY\NetworkService" CMD.EXE
SET PATH=%PATH%;C:\Program Files\edb\as18\bin
```

업그레이드 과정에서 `pg_upgrade`는 서비스 계정 사용자의 현재 작업 디렉터리에 파일을 씁니다. 서비스 계정 사용자가 쓰기 권한을 가진 디렉터리에서 `pg_upgrade`를 호출해야 합니다. 위 명령을 수행한 후, 서비스 계정 사용자가 파일을 쓸 권한이 있는 디렉터리로 이동합니다.

```shell
cd %TEMP%
```

## 6단계 — 일관성 검사 수행 (Step 6 - Perform a consistency check)

업그레이드를 시도하기 전에, 이전 클러스터와 새 클러스터가 호환되고 올바르게 구성되었는지 확인하기 위해 일관성 검사를 수행합니다. `--check` 옵션을 포함하여 `pg_upgrade`가 일관성 검사를 수행하도록 지시합니다.

다음 예는 Linux에서 일관성 검사를 수행하도록 `pg_upgrade`를 호출하는 것입니다.

```shell
pg_upgrade -d /var/lib/edb/as15/data
-D /var/lib/edb/as18/data -U enterprisedb
-b /usr/edb/as15/bin -B /usr/edb/as18/bin -p 5444 -P 5445 --check
```

명령이 성공하면 `*Clusters are compatible*`를 반환합니다.

Windows를 사용하는 경우, 공백이 포함된 디렉터리 이름은 따옴표로 묶습니다.

```shell
pg_upgrade.exe
-d "C:\Program Files\ PostgresPlus\15AS\data"
-D "C:\Program Files\edb\as18\data" -U enterprisedb
-b "C:\Program Files\PostgresPlus\15AS\bin"
-B "C:\Program Files\edb\as18\bin" -p 5444 -P 5445 --check
```

일관성 검사 과정에서 `pg_upgrade`는 발견된 불일치를 `pg_upgrade`를 호출한 디렉터리에 있는 파일에 기록합니다. 일관성 검사가 완료되면 파일을 검토하여 누락된 구성 요소나 업그레이드 충돌을 식별합니다. `pg_upgrade`를 호출하여 버전 업그레이드를 수행하기 전에 모든 충돌을 해결하십시오.

`pg_upgrade`가 누락된 구성 요소를 알리면, StackBuilder Plus를 사용하여 해당 구성 요소가 포함된 구성 요소를 추가할 수 있습니다. StackBuilder Plus를 사용하기 전에 EDB Postgres Advanced Server 서비스를 재시작합니다. 그런 다음 시작 메뉴에서 **EDB Postgres Advanced Server _version_ > StackBuilder Plus**를 선택하여 StackBuilder Plus를 엽니다. StackBuilder Plus 마법사의 화면 안내에 따라 누락된 구성 요소를 다운로드하여 설치합니다.

`pg_upgrade`가 클러스터가 호환됨을 확인한 후, 버전 업그레이드를 수행할 수 있습니다.

> **참고**
> `edb_wait_states`처럼 데이터베이스에 상시 연결을 유지하는 확장을 사용 중이라면, `pg_upgrade`를 사용하기 전에 비활성화하십시오. 업그레이드 중에는 데이터베이스에 어떤 연결도 설정되어 있지 않아야 합니다.

## 7단계 — pg_upgrade 실행 (Step 7 - Run pg_upgrade)

클러스터가 호환됨을 확인한 후, `pg_upgrade`를 호출하여 이전 클러스터를 새 버전의 EDB Postgres Advanced Server로 업그레이드할 수 있습니다.

Linux:

```shell
pg_upgrade -d /var/lib/edb/as15/data
-D /var/lib/edb/as18/data -U enterprisedb
-b /usr/edb/as15/bin -B /usr/edb/as18/bin -p 5444 -P 5445
```

Windows:

```shell
pg_upgrade.exe -d "C:\Program Files\PostgresPlus\15AS\data"
-D "C:\Program Files\edb\as18\data" -U enterprisedb
-b "C:\Program Files\PostgresPlus\15AS\bin"
-B "C:\Program Files\edb\as18\bin" -p 5444 -P 5445
```

`pg_upgrade`는 업그레이드 진행 상황을 화면에 표시합니다.

```shell
$ pg_upgrade -d /var/lib/edb/as15/data -D /var/lib/edb/as18/data -U

```

이 지점 이후 `pg_upgrade`가 실패하면, 계속하기 전에 새 클러스터를 다시 `initdb` 해야 합니다. 그렇지 않으면 다음과 같이 진행됩니다.

```shell
Performing Upgrade
------------------
Analyzing all rows in the new cluster                  ok

Deleting files from new pg_clog                        ok
Copying old pg_clog to new server                      ok

----------------

once you start the new server, consider running:
    analyze_new_cluster.sh

    delete_old_cluster.sh
```

`pg_upgrade`가 실행되는 동안, 업그레이드 중에 발견한 특수한 상황을 처리하는 SQL 스크립트를 생성할 수 있습니다. 예를 들어 이전 클러스터에 라지 오브젝트(large object)가 포함되어 있으면, 새 클러스터의 객체에 대한 기본 권한을 정의하는 스크립트를 호출해야 할 수 있습니다. 업그레이드 전 일관성 검사를 수행할 때, `pg_upgrade`는 수동으로 실행해야 할 수 있는 스크립트를 알려줍니다.

이 스크립트들은 `pg_upgrade`가 완료된 후에 호출해야 합니다. 스크립트를 호출하려면 EDB-PSQL 명령줄 클라이언트로 데이터베이스 슈퍼유저로 새 클러스터에 접속한 뒤, `\i` 옵션으로 각 스크립트를 호출합니다.

```shell
\i complete_path_to_script/script.sql
```

리빌드(rebuild) 스크립트가 완료되기 전까지, 리빌드 스크립트에서 참조하는 테이블에 접근하는 것은 일반적으로 안전하지 않습니다. 해당 테이블에 접근하면 잘못된 결과가 나오거나 성능이 저하될 수 있습니다. 리빌드 스크립트에서 참조하지 않는 테이블은 즉시 접근할 수 있습니다.

`pg_upgrade`가 업그레이드 과정을 완료하지 못하면, 이전 클러스터는 `$PGDATA/global/pg_control`이 `pg_control.old`로 이름이 바뀌고 각 테이블스페이스가 `tablespace.old`로 이름이 바뀐 것을 제외하고는 변경되지 않습니다. 호출 이전 상태로 되돌리려면 다음과 같이 합니다.

1. 새 클러스터가 생성한 테이블스페이스 디렉터리를 삭제합니다.
2. `$PGDATA/global/pg_control`의 `.old` 접미사를 제거하여 이름을 되돌립니다.
3. 이전 클러스터 테이블스페이스 디렉터리 이름의 `.old` 접미사를 제거하여 이름을 되돌립니다.
4. 업그레이드 실패 전에 이동된 데이터베이스 객체를 새 클러스터에서 제거합니다.

그런 다음, 발생한 업그레이드 충돌을 해결하고 업그레이드를 다시 시도합니다.

업그레이드가 완료되면 `pg_upgrade`는 새 클러스터를 VACUUM할 것을 권장할 수도 있습니다. 또한 이전 클러스터를 삭제할 수 있는 스크립트를 제공합니다.

> **참고**
> 이전 버전으로 되돌려야 할 경우를 대비하여, 이전 클러스터를 제거하기 전에 클러스터의 백업이 있는지, 그리고 클러스터가 업그레이드되었는지 반드시 확인하십시오.

## 8단계 — pg_hba.conf 파일의 인증 설정 복원 (Step 8 - Restore the authentication settings in the pg_hba.conf file)

`trust` 인증을 허용하기 위해 `pg_hba.conf` 파일을 수정했다면, 원하는 인증 설정을 반영하도록 `pg_hba.conf` 파일의 내용을 갱신합니다.

## 9단계 — 사용자 정의 테이블스페이스 이동 및 식별(선택) (Step 9 - Move and identify user-defined tablespaces (optional))

사용자 정의 테이블스페이스(user-defined tablespace)에 데이터가 저장되어 있다면, 업그레이드 후 테이블스페이스 파일을 수동으로 재배치해야 합니다. 파일을 새 위치로 옮기고 심볼릭 링크가 해당 파일을 가리키도록 갱신합니다. 심볼릭 링크는 클러스터의 `data` 디렉터리 아래 `pg_tblspc` 디렉터리에 위치합니다.

> **Windows의 경우**
> Windows는 ICU 버전 67.x를 사용합니다. pg_upgrade를 사용하여 메이저 버전 업그레이드를 수행하는 중이고 데이터베이스에 ICU 콜레이션(collation)을 사용하는 인덱스가 있다면, 업그레이드 후 해당 인덱스를 재색인(reindex)해야 합니다.
