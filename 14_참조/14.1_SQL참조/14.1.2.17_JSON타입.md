# JSON 타입 (JSON Types) — EPAS 18 Reference

| 이름 | 설명 |
| --- | --- |
| `json` | 입력 텍스트의 정확한 사본을 저장하는 JSON 데이터 타입 |
| `jsonb` | 분해된(binary) 형식으로 저장하여 처리에 최적화된 JSON 데이터 타입 |
| `jsonpath` | SQL/JSON 경로 표현식을 이진 표현으로 저장하는 타입 |

## 개요 (Overview)

JSON 데이터 타입은 [RFC 7159](https://datatracker.ietf.org/doc/html/rfc7159)에 명시된 JSON(JavaScript Object Notation) 데이터를 저장하기 위한 것입니다. 이러한 데이터는 `text`로도 저장할 수 있지만, JSON 데이터 타입은 저장되는 각 값이 JSON 규칙에 따라 유효한지 강제한다는 장점이 있습니다. 또한 이 데이터 타입에 저장된 데이터에 대해 사용할 수 있는 다양한 JSON 전용 함수와 연산자가 있습니다.

EDB Postgres Advanced Server는 JSON 데이터를 저장하기 위한 두 가지 타입 `json`과 `jsonb`를 제공합니다. 또한 이 데이터 타입에 대한 효율적인 쿼리 메커니즘을 구현하기 위해 `jsonpath` 데이터 타입도 제공합니다.

`json`과 `jsonb` 데이터 타입은 입력으로 *거의* 동일한 값 집합을 받습니다. 실질적인 주요 차이는 효율성입니다. `json` 데이터 타입은 입력 텍스트의 정확한 사본을 저장하므로 처리 함수가 실행할 때마다 다시 파싱해야 합니다. 반면 `jsonb` 데이터는 분해된 이진(binary) 형식으로 저장되어 입력 시 변환 오버헤드로 약간 느리지만, 다시 파싱할 필요가 없어 처리가 훨씬 빠릅니다. `jsonb`는 또한 인덱싱을 지원하며, 이는 상당한 이점이 될 수 있습니다.

`json` 타입은 입력 텍스트의 정확한 사본을 저장하므로 토큰 사이의 의미상 중요하지 않은 공백과 JSON 객체 내 키의 순서를 보존합니다. 또한 값 내부의 JSON 객체가 동일한 키를 두 번 이상 포함하면 모든 키/값 쌍이 유지됩니다(처리 함수는 마지막 값을 유효한 것으로 간주). 반면 `jsonb`는 공백을 보존하지 않고, 객체 키의 순서를 보존하지 않으며, 중복 객체 키를 유지하지 않습니다. 입력에 중복 키가 지정되면 마지막 값만 유지됩니다.

일반적으로 대부분의 애플리케이션은, 객체 키의 순서에 대한 레거시 가정 같은 상당히 특수한 요구가 없는 한, JSON 데이터를 `jsonb`로 저장하는 것을 선호해야 합니다.

RFC 7159는 JSON 문자열이 UTF8로 인코딩되어야 한다고 명시합니다. 따라서 데이터베이스 인코딩이 UTF8이 아니면 JSON 타입이 JSON 명세를 엄격히 준수하는 것은 불가능합니다. 데이터베이스 인코딩으로 표현할 수 없는 문자를 직접 포함하려는 시도는 실패합니다.

텍스트 JSON 입력을 `jsonb`로 변환할 때, RFC 7159가 기술하는 원시(primitive) 타입은 다음 표와 같이 네이티브 PostgreSQL 타입으로 매핑됩니다. 따라서 `jsonb`에는 `json` 타입에는 적용되지 않는 몇 가지 사소한 제약이 추가됩니다. 특히 `jsonb`는 PostgreSQL `numeric` 데이터 타입의 범위를 벗어나는 숫자를 거부하지만 `json`은 그렇지 않습니다.

**표: JSON 원시 타입과 대응하는 PostgreSQL 타입**

| JSON 원시 타입 | PostgreSQL 타입 | 비고 |
| --- | --- | --- |
| `string` | `text` | `\u0000`은 허용되지 않으며, 데이터베이스 인코딩에 없는 문자를 나타내는 Unicode 이스케이프도 허용되지 않음 |
| `number` | `numeric` | `NaN`, `infinity` 값은 허용되지 않음 |
| `boolean` | `boolean` | 소문자 `true`, `false` 표기만 허용 |
| `null` | (없음) | SQL `NULL`은 별개의 개념 |

## JSON 입력 및 출력 구문 (JSON Input and Output Syntax)

JSON 데이터 타입의 입출력 구문은 RFC 7159에 명시된 것과 같습니다. 다음은 모두 유효한 `json`(또는 `jsonb`) 표현식입니다.

```sql
-- 단순 스칼라/원시 값
-- 원시 값은 숫자, 따옴표로 묶인 문자열, true, false, null일 수 있습니다.
SELECT '5'::json;

-- 0개 이상의 요소로 구성된 배열(요소가 같은 타입일 필요는 없음)
SELECT '[1, 2, "foo", null]'::json;

-- 키와 값 쌍을 포함하는 객체
-- 객체 키는 항상 따옴표로 묶인 문자열이어야 합니다.
SELECT '{"bar": "baz", "balance": 7.77, "active": false}'::json;

-- 배열과 객체는 임의로 중첩될 수 있습니다.
SELECT '{"foo": [true, "bar"], "tags": {"a": 1, "b": null}}'::json;
```

앞서 설명했듯이 JSON 값을 입력한 뒤 추가 처리 없이 출력하면, `json`은 입력된 것과 동일한 텍스트를 출력하지만 `jsonb`는 공백 같은 의미상 중요하지 않은 세부 사항을 보존하지 않습니다. 예를 들어 다음 차이에 주목하십시오.

```sql
SELECT '{"bar": "baz", "balance": 7.77, "active":false}'::json;
                      json
-------------------------------------------------
 {"bar": "baz", "balance": 7.77, "active":false}
(1 row)

SELECT '{"bar": "baz", "balance": 7.77, "active":false}'::jsonb;
                      jsonb
--------------------------------------------------
 {"bar": "baz", "active": false, "balance": 7.77}
(1 row)
```

주목할 만한 의미상 중요하지 않은 세부 사항 하나는, `jsonb`에서 숫자가 기저 `numeric` 타입의 동작에 따라 출력된다는 점입니다. 실무적으로 이는 `E` 표기법으로 입력된 숫자가 해당 표기 없이 출력됨을 의미합니다.

```sql
SELECT '{"reading": 1.230e-5}'::json, '{"reading": 1.230e-5}'::jsonb;
         json          |          jsonb
-----------------------+-------------------------
 {"reading": 1.230e-5} | {"reading": 0.00001230}
(1 row)
```

JSON 값을 구성·처리하기 위한 내장 함수와 연산자 목록은 [JSON 함수와 연산자](https://www.postgresql.org/docs/18/functions-json.html)를 참고하십시오.

## JSON 문서 설계 (Designing JSON Documents)

데이터를 JSON으로 표현하면 전통적인 관계형 데이터 모델보다 훨씬 유연할 수 있으며, 요구 사항이 유동적인 환경에서 매력적입니다. 최대한의 유연성이 필요한 애플리케이션이라도, JSON 문서가 어느 정도 고정된 구조를 갖는 것을 권장합니다. 예측 가능한 구조는 테이블 내 "문서" 집합을 유용하게 요약하는 쿼리를 작성하기 쉽게 만듭니다.

JSON 데이터는 테이블에 저장될 때 다른 데이터 타입과 동일한 동시성 제어 고려 사항의 대상이 됩니다. 큰 문서를 저장하는 것도 가능하지만, 모든 갱신은 행 전체에 대한 행 수준 잠금을 획득한다는 점에 유의하십시오. 갱신 트랜잭션 간의 잠금 경합을 줄이려면 JSON 문서를 관리 가능한 크기로 제한하는 것을 고려하십시오.

## jsonb의 포함(Containment)과 존재(Existence)

*포함(containment)* 테스트는 `jsonb`의 중요한 기능입니다. `json` 타입에는 이에 대응하는 기능 집합이 없습니다. 포함은 한 `jsonb` 문서가 다른 문서를 그 안에 포함하는지를 테스트합니다. 다음 예는 표시된 경우를 제외하고 모두 true를 반환합니다.

```sql
-- 단순 스칼라/원시 값은 동일한 값만 포함합니다.
SELECT '"foo"'::jsonb @> '"foo"'::jsonb;

-- 오른쪽 배열이 왼쪽 배열에 포함됩니다.
SELECT '[1, 2, 3]'::jsonb @> '[1, 3]'::jsonb;

-- 배열 요소의 순서는 중요하지 않으므로 이것도 true입니다.
SELECT '[1, 2, 3]'::jsonb @> '[3, 1]'::jsonb;

-- 중복 배열 요소도 상관없습니다.
SELECT '[1, 2, 3]'::jsonb @> '[1, 2, 2]'::jsonb;

-- 오른쪽의 단일 쌍 객체가 왼쪽 객체에 포함됩니다.
SELECT '{"product": "PostgreSQL", "version": 9.4, "jsonb": true}'::jsonb @> '{"version": 9.4}'::jsonb;

-- 오른쪽 배열은 왼쪽 배열에 포함된 것으로 간주되지 않습니다(유사 배열이 중첩되어 있어도).
SELECT '[1, 2, [1, 3]]'::jsonb @> '[1, 3]'::jsonb;  -- false 반환

-- 그러나 중첩 계층을 하나 더 두면 포함됩니다.
SELECT '[1, 2, [1, 3]]'::jsonb @> '[[1, 3]]'::jsonb;

-- 마찬가지로 여기서는 포함으로 보고되지 않습니다.
SELECT '{"foo": {"bar": "baz"}}'::jsonb @> '{"bar": "baz"}'::jsonb;  -- false 반환

-- 최상위 키와 빈 객체는 포함됩니다.
SELECT '{"foo": {"bar": "baz"}}'::jsonb @> '{"foo": {}}'::jsonb;
```

일반 원칙은, 포함되는 객체가 포함하는 객체와 구조·데이터 내용 면에서 일치해야 한다는 것입니다(포함하는 객체에서 일부 비일치 배열 요소나 키/값 쌍을 버린 뒤일 수 있음). 다만 포함 매칭 시 배열 요소의 순서는 중요하지 않고, 중복 배열 요소는 사실상 한 번만 고려됩니다.

일반 원칙에 대한 특별한 예외로, 배열은 원시 값을 포함할 수 있습니다.

```sql
-- 이 배열은 원시 문자열 값을 포함합니다.
SELECT '["foo", "bar"]'::jsonb @> '"bar"'::jsonb;

-- 이 예외는 상호적이지 않습니다 — 여기서는 비포함으로 보고됩니다.
SELECT '"bar"'::jsonb @> '["bar"]'::jsonb;  -- false 반환
```

`jsonb`에는 포함과 유사한 *존재(existence)* 연산자도 있습니다. 이는 주어진 문자열(`text` 값)이 `jsonb` 값의 최상위에서 객체 키 또는 배열 요소로 나타나는지를 테스트합니다.

```sql
-- 문자열이 배열 요소로 존재:
SELECT '["foo", "bar", "baz"]'::jsonb ? 'bar';

-- 문자열이 객체 키로 존재:
SELECT '{"foo": "bar"}'::jsonb ? 'foo';

-- 객체 값은 고려되지 않습니다.
SELECT '{"foo": "bar"}'::jsonb ? 'bar';  -- false 반환
```

키나 요소가 많을 때는, 배열보다 JSON 객체가 포함·존재 테스트에 더 적합합니다. 배열과 달리 객체는 내부적으로 검색에 최적화되어 있어 선형 검색이 필요하지 않기 때문입니다.

## jsonb 인덱싱 (jsonb Indexing)

GIN 인덱스는 많은 수의 `jsonb` 문서 내에서 키 또는 키/값 쌍을 효율적으로 검색하는 데 사용할 수 있습니다. 서로 다른 성능·유연성 균형을 제공하는 두 가지 GIN "연산자 클래스"가 제공됩니다.

`jsonb`의 기본 GIN 연산자 클래스는 키 존재 연산자 `?`, `?|`, `?&`, 포함 연산자 `@>`, `jsonpath` 매치 연산자 `@?`, `@@`를 사용하는 쿼리를 지원합니다.

```sql
CREATE INDEX idxgin ON api USING GIN (jdoc);
```

기본이 아닌 GIN 연산자 클래스 `jsonb_path_ops`는 키 존재 연산자를 지원하지 않지만 `@>`, `@?`, `@@`는 지원합니다.

```sql
CREATE INDEX idxginp ON api USING GIN (jdoc jsonb_path_ops);
```

`api`라는 테이블의 `jdoc`라는 `jsonb` 컬럼에 문서를 저장하고 GIN 인덱스를 생성하면, 다음과 같은 쿼리가 인덱스를 활용할 수 있습니다.

```sql
-- 키 "company"의 값이 "Magnafone"인 문서 찾기
SELECT jdoc->'guid', jdoc->'name' FROM api WHERE jdoc @> '{"company": "Magnafone"}';
```

다음과 같은 쿼리에는 인덱스를 사용할 수 없습니다. 연산자 `?`는 인덱싱 가능하지만 인덱싱된 컬럼 `jdoc`에 직접 적용되지 않기 때문입니다.

```sql
-- 키 "tags"가 키 또는 배열 요소 "qui"를 포함하는 문서 찾기
SELECT jdoc->'guid', jdoc->'name' FROM api WHERE jdoc -> 'tags' ? 'qui';
```

그러나 표현식 인덱스를 적절히 사용하면 위 쿼리도 인덱스를 사용할 수 있습니다.

```sql
CREATE INDEX idxgintags ON api USING GIN ((jdoc -> 'tags'));
```

또 다른 접근은 포함을 활용하는 것입니다.

```sql
-- 키 "tags"가 배열 요소 "qui"를 포함하는 문서 찾기
SELECT jdoc->'guid', jdoc->'name' FROM api WHERE jdoc @> '{"tags": ["qui"]}';
```

`jdoc` 컬럼에 대한 단순 GIN 인덱스가 이 쿼리를 지원할 수 있습니다. `jsonb_path_ops`는 기본 연산자 클래스 `jsonb_ops`에 비해 인덱스 크기가 작고 검색 특이성이 좋아 일반적으로 성능이 더 우수하지만, 값이 없는 JSON 구조(예: `{"a": {}}`)에 대해서는 인덱스 항목을 만들지 않는 단점이 있습니다.

`jsonb`는 `btree`와 `hash` 인덱스도 지원합니다. 이들은 완전한 JSON 문서의 동등성을 확인하는 것이 중요한 경우에만 대체로 유용합니다. `jsonb` 값의 `btree` 정렬 순서는 다음과 같습니다.

```text
Object > Array > Boolean > Number > String > null
```

## jsonb 서브스크립팅 (jsonb Subscripting)

`jsonb` 데이터 타입은 요소를 추출·수정하기 위한 배열 스타일 서브스크립팅 표현식을 지원합니다. 서브스크립팅 표현식을 연결하여 중첩 값을 나타낼 수 있습니다. `jsonb` 값이 배열이면 숫자 서브스크립트는 0에서 시작하고, 음의 정수는 배열의 마지막 요소부터 역순으로 셉니다. 슬라이스 표현식은 지원되지 않습니다. 서브스크립팅 표현식의 결과는 항상 `jsonb` 데이터 타입입니다.

`UPDATE` 문은 `SET` 절에서 서브스크립팅을 사용하여 `jsonb` 값을 수정할 수 있습니다.

```sql
-- 키로 객체 값 추출
SELECT ('{"a": 1}'::jsonb)['a'];

-- 키 경로로 중첩 객체 값 추출
SELECT ('{"a": {"b": {"c": 1}}}'::jsonb)['a']['b']['c'];

-- 인덱스로 배열 요소 추출
SELECT ('[1, "2", null]'::jsonb)[1];

-- 키로 객체 값 갱신. 할당하는 값도 jsonb 타입이어야 하므로 '1'에 따옴표가 필요합니다.
UPDATE table_name SET jsonb_field['key'] = '1';

-- WHERE 절에서 서브스크립팅으로 레코드 필터링. 서브스크립팅 결과가 jsonb이므로
-- 비교 대상 값도 jsonb여야 합니다.
SELECT * FROM table_name WHERE jsonb_field['key'] = '"value"';
```

서브스크립팅을 통한 `jsonb` 할당은 일부 예외 상황을 `jsonb_set`과 다르게 처리합니다. 원본 `jsonb` 값이 `NULL`이면, 서브스크립팅을 통한 할당은 서브스크립트 키가 암시하는 타입(객체 또는 배열)의 빈 JSON 값인 것처럼 진행됩니다.

```sql
-- jsonb_field가 NULL이었다면 이제 {"a": 1}이 됩니다.
UPDATE table_name SET jsonb_field['a'] = '1';

-- jsonb_field가 NULL이었다면 이제 [1]이 됩니다.
UPDATE table_name SET jsonb_field[0] = '1';
```

## 변환 (Transforms)

`jsonb` 타입에 대해 여러 절차적 언어용 변환(transform)을 구현하는 추가 확장이 제공됩니다. PL/Perl용 확장은 `jsonb_plperl`, `jsonb_plperlu`이며, `jsonb` 값을 Perl 배열·해시·스칼라로 매핑합니다. PL/Python용 확장은 `jsonb_plpython3u`이며, `jsonb` 값을 Python 딕셔너리·리스트·스칼라로 매핑합니다. 이 중 `jsonb_plperl`은 "신뢰됨(trusted)"으로 간주되어 현재 데이터베이스에 대한 `CREATE` 권한이 있는 비슈퍼유저가 설치할 수 있고, 나머지는 설치에 슈퍼유저 권한이 필요합니다.

## jsonpath 타입 (jsonpath Type)

`jsonpath` 타입은 JSON 데이터를 효율적으로 쿼리하기 위한 SQL/JSON 경로 언어를 구현합니다. 파싱된 SQL/JSON 경로 표현식의 이진 표현을 제공하여, 경로 엔진이 SQL/JSON 쿼리 함수로 추가 처리할 항목을 JSON 데이터에서 검색할 수 있게 합니다.

SQL/JSON 경로 술어와 연산자의 의미는 일반적으로 SQL을 따르지만, JSON 데이터를 자연스럽게 다루기 위해 일부 JavaScript 관례를 사용합니다.

- 점(`.`)은 멤버 접근에 사용됩니다.
- 대괄호(`[]`)는 배열 접근에 사용됩니다.
- SQL/JSON 배열은 일반 SQL 배열이 1부터 시작하는 것과 달리 0부터 시작합니다.

경로 표현식은 보통 SQL 문자열 리터럴로 작성되므로 작은따옴표로 묶어야 합니다. 경로 표현식은 다음과 같은 경로 요소의 시퀀스로 구성됩니다: JSON 원시 타입의 경로 리터럴, 경로 변수, 접근자(accessor) 연산자, `jsonpath` 연산자·메서드, 괄호.

**표: jsonpath 변수**

| 변수 | 설명 |
| --- | --- |
| `$` | 쿼리 대상 JSON 값(컨텍스트 항목)을 나타내는 변수 |
| `$varname` | 명명된 변수. 여러 JSON 처리 함수의 `vars` 파라미터로 값을 설정할 수 있음 |
| `@` | 필터 표현식에서 경로 평가 결과를 나타내는 변수 |

**표: jsonpath 접근자**

| 접근자 연산자 | 설명 |
| --- | --- |
| `.key` / `."$varname"` | 지정한 키의 객체 멤버를 반환하는 멤버 접근자 |
| `.*` | 현재 객체 최상위의 모든 멤버 값을 반환하는 와일드카드 멤버 접근자 |
| `.**` | JSON 계층의 모든 수준을 처리하여 중첩 수준과 무관하게 모든 멤버 값을 반환(PostgreSQL 확장) |
| `[subscript, ...]` | 배열 요소 접근자. `index` 또는 `start_index to end_index` 형태 사용 |
| `[*]` | 모든 배열 요소를 반환하는 와일드카드 배열 요소 접근자 |

`jsonpath` 표현식을 SQL/JSON 쿼리 함수와 함께 사용하는 방법은 [SQL/JSON 경로 언어](https://www.postgresql.org/docs/18/functions-json.html#FUNCTIONS-SQLJSON-PATH)를 참고하십시오.
