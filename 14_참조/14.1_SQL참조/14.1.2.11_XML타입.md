| 이름 | 네이티브 | 별칭 | 설명 |

| `XMLTYPE` | ✅ |  | XML 데이터를 저장하는 데 사용하는 데이터 타입 |

## 개요 (Overview)

`XMLTYPE` 데이터 타입은 XML 데이터를 저장하는 데 사용됩니다. 문자 필드에 XML 데이터를 저장하는 것에 비한 장점은, 입력 값이 얼마나 잘 형성되었는지(well-formed) 검사한다는 것입니다. 또한 지원 함수들이 타입 안전한 연산을 수행합니다.

XML 타입은 XML 표준이 정의하는 잘 형성된 "문서(documents)"뿐 아니라 XML 표준의 `XMLDoc content` 생성 규칙으로 정의되는 "콘텐츠(content)" 조각도 저장할 수 있습니다. 대략적으로 이는 콘텐츠 조각이 둘 이상의 최상위 요소나 문자 노드를 가질 수 있음을 의미합니다.

※ 주의: XMLPARSE 함수는 xml 타입 값을 반환합니다. EPAS에서는 xml 타입과 XMLTYPE 타입 간의 묵시적 형변환이 지원되지 않으므로 XMLTYPE 컬럼에 저장할 경우 XMLTYPE 생성자를 사용해야 합니다.

이 예는 `XMLTYPE` 컬럼이 있는 테이블을 생성하고 행을 삽입하는 것을 보여줍니다:

```sql
CREATE TABLE books (
    content         XMLTYPE
);

-- XMLPARSE의 결과는 xml 타입이므로 XMLTYPE 컬럼에 직접 저장할 수 없음
INSERT INTO books VALUES ( XMLTYPE('<book><title>Manual</title></book>'));

SELECT * FROM books;
```

출력(Output):

```text
              content               
------------------------------------
 <book><title>Manual</title></book>
(1 row)
```

## XML 값 생성 (Creating XML Values)

문자 데이터로부터 xml 타입 값을 생성하려면 XMLPARSE 함수를 사용합니다. XMLPARSE의 결과는 xml 타입입니다.
(※ XMLTYPE 컬럼에 저장하려면 XMLTYPE 생성자를 사용해야 합니다.) :

```text
XMLPARSE ( { DOCUMENT | CONTENT } value)
```

예:

```text
XMLPARSE (DOCUMENT '<?xml version="1.0"?><book><title>Manual</title><chapter>...</chapter></book>')
XMLPARSE (CONTENT 'abc<foo>bar</foo><bar>foo</bar>')
```

이것이 SQL 표준에 따라 문자열을 XML 값으로 변환하는 유일한 방법이지만, PostgreSQL 고유 구문도 사용할 수 있습니다:

```text
xml '<foo>bar</foo>'
'<foo>bar</foo>'::xml
```

XML 타입은 입력 값이 문서 타입 선언(DTD)을 지정하더라도 DTD에 대해 입력 값을 검증하지 않습니다. 또한 현재 XML Schema 같은 다른 XML 스키마 언어에 대한 검증도 기본 제공되지 않습니다.

역연산, 즉 XML에서 문자열 값을 생성하는 것은 `XMLSERIALIZE` 함수를 사용합니다:

```text
XMLSERIALIZE ( { DOCUMENT | CONTENT } value AS type [ [ NO ] INDENT ] )
```

`type`은 `character`, `character varying`, `text`(또는 이들 중 하나의 별칭)일 수 있습니다. 마찬가지로 SQL 표준에 따르면 이것이 XML 타입과 문자 타입 사이를 변환하는 유일한 방법이지만, PostgreSQL은 값을 단순히 캐스트하는 것도 허용합니다.

`INDENT` 옵션은 결과를 보기 좋게 정렬(pretty-print)하게 하는 반면, `NO INDENT`(기본값)는 원본 입력 문자열을 그대로 내보냅니다. 문자 타입으로의 캐스트도 마찬가지로 원본 문자열을 생성합니다.

문자열 값을 각각 `XMLPARSE`나 `XMLSERIALIZE`를 거치지 않고 XML 타입으로/에서 캐스트할 때, `DOCUMENT` 대 `CONTENT` 선택은 "XML 옵션" 세션 구성 파라미터에 의해 결정되며, 이는 표준 명령으로 설정할 수 있습니다:

```text
SET XML OPTION { DOCUMENT | CONTENT };
```

또는 더 PostgreSQL스러운 구문:

```text
SET xmloption TO { DOCUMENT | CONTENT };
```

기본값은 `CONTENT`이므로 모든 형태의 XML 데이터가 허용됩니다.

## XMLType 서브프로그램 (XMLType subprograms)

버전 17부터 XMLType은 객체 타입으로 호출될 수 있으며 사전 정의된 멤버 함수와 생성자를 갖습니다.

이 표는 XMLType의 멤버 함수와 생성자를 요약합니다.

| 메서드 | 타입 | 설명 |
| --- | --- | --- |
| `EXISTSNODE` | 멤버 함수 | `XMLType` 인스턴스와 `XPath`를 받아, `XPath` 적용 결과가 비어 있지 않은 노드 집합인지를 나타내기 위해 1 또는 0을 반환 |
| `EXTRACT_XML` | 멤버 함수 | `XMLType` 인스턴스와 `XPath`를 받아 `XPath` 표현식을 적용하고 결과를 `XMLType`으로 반환 |
| `GETCLOBVAL()` | 멤버 함수 | `XMLType` 인스턴스의 값을 CLOB로 반환 |
| `GETNUMBERVAL()` | 멤버 함수 | `XMLType` 인스턴스의 값을 NUMBER로 반환. 이 연산은 입력 `XMLType` 인스턴스가 단순 텍스트 노드를 포함하고 숫자로 성공적으로 변환될 수 있는 경우에만 유효 |
| `GETSTRINGVAL()` | 멤버 함수 | `XMLType` 인스턴스의 값을 문자열로 반환 |
| `XMLTYPE` | 생성자 함수 | `XMLType` 데이터 타입의 인스턴스를 생성. 생성자는 XML을 CLOB, TEXT 또는 객체 타입으로 받음 |

### EXISTSNODE

이 멤버 함수는 연관된 노드의 존재를 검증합니다.

**구문:**

```text
MEMBER FUNCTION EXISTSNODE(ip_xpath TEXT, ip_nsp TEXT[] DEFAULT '{}'::TEXT[]) RETURN INTEGER
```

여기서, `ip_xpath`는 테스트할 표현식입니다. `ip_nsp`는 선택적 네임스페이스 매핑입니다.

### EXTRACT_XML

**구문:**

```text
MEMBER FUNCTION EXTRACT_XML(ip_xpath TEXT, ip_nsp TEXT[] DEFAULT '{}'::TEXT[]) RETURN SET OF XMLTYPE
```

여기서, `ip_xpath`는 적용할 표현식입니다. `ip_nsp`는 네임스페이스 매핑 정보에 대한 선택적 접두사입니다.

### GETCLOBVAL()

**구문:**

```text
MEMBER FUNCTION GETCLOBVAL() RETURN CLOB
```

### GETNUMBERVAL()

**구문:**

```text
MEMBER FUNCTION GETNUMBERVAL() RETURN NUMERIC
```

### GETSTRINGVAL()

**구문:**

```text
MEMBER FUNCTION GETSTRINGVAL() RETURN VARCHAR2
```

### 예제 - 멤버 함수 (Examples - Member functions)

이 예는 XMLTYPE 데이터 타입으로 테이블을 만들고 데이터를 삽입하는 방법을 보여줍니다.

```sql
CREATE TABLE person_xmltype (person_id integer,person_data xmltype);
INSERT INTO person_xmltype(person_id, person_data)
VALUES (1, xmltype('<PDRecord><PDName>test_user1</PDName><PDID>1</PDID><PDEmail>test_user1@testmail.com</PDEmail></PDRecord>'::xml)),
       (2, xmltype('<PDRecord><PDName>test_user2</PDName><PDID>2</PDID><PDEmail>test_user2@testmail.com</PDEmail></PDRecord>'::xml)),
       (3, xmltype('<PDRecord><PDName>test_user3</PDName><PDID>3</PDID><PDEmail>test_user3@testmail.com</PDEmail></PDRecord>'::xml)),
       (4, xmltype('<PDRecord><PDName>test_user4</PDName><PDID>4</PDID><PDEmail>test_user4@testmail.com</PDEmail></PDRecord>'::TEXT)),
       (5, xmltype('<PDRecord><PDName>test_user5</PDName><PDID>5</PDID><PDEmail>test_user5@testmail.com</PDEmail></PDRecord>'::CLOB)) ;
```

다음 예들은 테이블에 저장된 XMLTYPE 데이터를 보기 위해 EXTRACT_XML 멤버 함수를 사용하는 방법을 보여줍니다.

```sql
-- Extract_xml()
SELECT person_data.EXTRACT_XML('/PDRecord/PDName') FROM person_xmltype;
```

출력(Output):

```text
extract_xml
-----------------------------
<PDName>test_user1</PDName>
<PDName>test_user2</PDName>
<PDName>test_user3</PDName>
<PDName>test_user4</PDName>
<PDName>test_user5</PDName>
(5 rows)
```

```sql
SELECT EXTRACT_XML(person_data, '/PDRecord/PDName') FROM person_xmltype;
```

출력(Output):

```text

<PDName>test_user2</PDName>
<PDName>test_user3</PDName>
```

```sql
xmltype_data XMLTYPE;
```

## 인코딩 처리 (Encoding Handling)

클라이언트, 서버, 그리고 그 사이를 통과하는 XML 데이터에서 여러 문자 인코딩을 다룰 때 주의하십시오. 서버에 쿼리를, 클라이언트에 쿼리 결과를 전달하는 일반 모드인 텍스트 모드를 사용할 때, PostgreSQL은 클라이언트와 서버 사이에 오가는 모든 문자 데이터를 각 끝단의 문자 인코딩으로 변환합니다. 여기에는 XML 값의 문자열 표현이 포함됩니다. 이는 통상적으로, 임베디드 인코딩 선언이 변경되지 않으므로 문자 데이터가 클라이언트와 서버 사이를 이동하며 다른 인코딩으로 변환될 때 XML 데이터에 포함된 인코딩 선언이 무효화될 수 있음을 의미합니다. 이 동작에 대처하기 위해, XML 타입에 입력으로 제시된 문자열에 포함된 인코딩 선언은 무시되며 콘텐츠는 현재 서버 인코딩인 것으로 가정됩니다. 결과적으로 올바른 처리를 위해 XML 데이터의 문자열은 현재 클라이언트 인코딩으로 클라이언트에서 전송되어야 합니다. 문서를 서버로 보내기 전에 현재 클라이언트 인코딩으로 변환하거나, 클라이언트 인코딩을 적절히 조정하는 것은 클라이언트의 책임입니다. 출력 시 XML 타입 값에는 인코딩 선언이 없으며, 클라이언트는 모든 데이터가 현재 클라이언트 인코딩이라고 가정해야 합니다.

바이너리 모드를 사용해 쿼리 파라미터를 서버로, 쿼리 결과를 클라이언트로 전달할 때는 인코딩 변환이 수행되지 않으므로 상황이 다릅니다. 이 경우 XML 데이터의 인코딩 선언이 준수되며, 없으면 데이터가 UTF-8인 것으로 가정됩니다(XML 표준이 요구하는 대로. PostgreSQL은 UTF-16을 지원하지 않음에 유의). 출력 시 데이터에는 클라이언트 인코딩을 지정하는 인코딩 선언이 있으며, 클라이언트 인코딩이 UTF-8인 경우에는 생략됩니다.

XML 데이터 인코딩, 클라이언트 인코딩, 서버 인코딩이 동일하면 PostgreSQL로 XML 데이터를 처리하는 것이 오류가 적고 더 효율적입니다. XML 데이터는 내부적으로 UTF-8로 처리되므로, 서버 인코딩도 UTF-8이면 계산이 가장 효율적입니다.

##### 참고 (Note)

서버 인코딩이 UTF-8이 아닐 때 일부 XML 관련 함수는 비-ASCII 데이터에서 전혀 동작하지 않을 수 있습니다. 특히 `xmltable()`과 `xpath()`에서 문제가 되는 것으로 알려져 있습니다.

## XML 값 접근 (Accessing XML Values)

XML 데이터 타입은 비교 연산자를 전혀 제공하지 않는다는 점에서 특이합니다. 이는 XML 데이터에 대해 잘 정의되고 보편적으로 유용한 비교 알고리즘이 없기 때문입니다. 그 결과 중 하나는 XML 컬럼을 검색 값과 비교하여 행을 조회할 수 없다는 것입니다. 따라서 XML 값에는 일반적으로 ID 같은 별도의 키 필드가 동반되어야 합니다. XML 값을 비교하는 대안은 먼저 문자열로 변환하는 것이지만, 문자열 비교는 유용한 XML 비교 방법과는 거의 관련이 없다는 점에 유의하십시오.

XML 데이터 타입에 비교 연산자가 없으므로 이 타입의 컬럼에 직접 인덱스를 만들 수 없습니다. XML 데이터의 빠른 검색이 필요하면, 가능한 우회책으로 표현식을 문자열 타입으로 캐스트하여 인덱싱하거나 XPath 표현식을 인덱싱하는 방법이 있습니다. 물론 실제 쿼리는 인덱싱된 표현식으로 검색하도록 조정해야 합니다.

PostgreSQL의 텍스트 검색 기능도 XML 데이터의 전체 문서 검색 속도를 높이는 데 사용할 수 있습니다. 다만 필요한 전처리 지원은 아직 PostgreSQL 배포판에서 제공되지 않습니다.
