# DBMS_RLS — EPAS 18 내장 패키지

> 원문: [EPAS v18 — Reference › Oracle compatibility › Built-in packages › DBMS_RLS](https://www.enterprisedb.com/docs/epas/latest/reference/oracle_compatibility_reference/epas_compat_bip_guide/03_built-in_packages/14_dbms_rls/)
> EPAS v18 공식 문서의 한글 **전문 번역**입니다. 패키지·프로시저·역할 이름은 원문 그대로 보존했습니다.

`DBMS_RLS` 패키지를 사용하면 특정 EDB Postgres Advanced Server 데이터베이스 객체에 Virtual Private Database를 구현할 수 있습니다.

EDB Postgres Advanced Server의 `DBMS_RLS` 구현은 Oracle 버전과 비교할 때 부분적인 구현입니다. 표에 나열된 함수와 프로시저만 지원됩니다.

| 함수/프로시저 | 함수 또는 프로시저 | 반환 타입 | 설명 |
| --- | --- | --- | --- |
| `ADD_POLICY(object_schema, object_name, policy_name, function_schema, policy_function [, statement_types [, update_check [, enable [, static_policy [, policy_type [, long_predicate [, sec_relevant_cols [, sec_relevant_cols_opt ]]]]]]]])` | 프로시저 | 해당 없음 | 데이터베이스 객체에 보안 정책을 추가합니다. |
| `DROP_POLICY(object_schema, object_name, policy_name)` | 프로시저 | 해당 없음 | 데이터베이스 객체에서 보안 정책을 제거합니다. |
| `ENABLE_POLICY(object_schema, object_name, policy_name, enable)` | 프로시저 | 해당 없음 | 보안 정책을 활성화하거나 비활성화합니다. |

_Virtual Private Database_ 는 보안 정책을 사용하는 세분화된 접근 제어(fine-grained access control)의 한 유형입니다. Virtual Private Database에서 _세분화된 접근 제어_ 란 보안 정책으로 정의된 특정 행 수준까지 데이터에 대한 접근을 제어할 수 있음을 의미합니다.

보안 정책을 인코딩하는 규칙은 _정책 함수(policy function)_ 에 정의되며, 이는 특정 입력 매개변수와 반환 값을 가진 SPL 함수입니다. _보안 정책(security policy)_ 은 정책 함수를 특정 데이터베이스 객체(일반적으로 테이블)에 명명하여 연결한 것입니다.

##### 참고 (Note)

EDB Postgres Advanced Server에서는 SQL, PL/pgSQL, SPL 등 EDB Postgres Advanced Server가 지원하는 모든 언어로 정책 함수를 작성할 수 있습니다.

##### 참고 (Note)

EDB Postgres Advanced Server Virtual Private Database에서 현재 지원하는 데이터베이스 객체는 테이블입니다. 뷰나 시노님(synonym)에는 정책을 적용할 수 없습니다.

Virtual Private Database에는 다음과 같은 장점이 있습니다.

- 세분화된 수준의 보안을 제공합니다. `GRANT` 명령으로 부여하는 데이터베이스 객체 수준 권한은 데이터베이스 객체의 전체 인스턴스에 대한 접근 권한을 결정하는 반면, Virtual Private Database는 데이터베이스 객체 인스턴스의 개별 행에 대한 접근 제어를 제공합니다.
- SQL 명령의 타입(`INSERT`, `UPDATE`, `DELETE` 또는 `SELECT`)에 따라 서로 다른 보안 정책을 적용할 수 있습니다.
- 데이터베이스 객체에 접근하는 애플리케이션의 세션 사용자와 같은 요인에 따라, 데이터베이스 객체에 영향을 주는 각 해당 SQL 명령마다 보안 정책이 동적으로 달라질 수 있습니다.
- 보안 정책 호출은 데이터베이스 객체에 접근하는 모든 애플리케이션에 투명합니다. 따라서 보안 정책을 적용하기 위해 개별 애플리케이션을 수정할 필요가 없습니다.
- 보안 정책이 활성화되면, 애플리케이션(신규 애플리케이션 포함)은 아래 참고에 설명된 시스템 권한을 제외하고는 보안 정책을 우회할 수 없습니다.
- 슈퍼유저조차도 아래 참고에 설명된 시스템 권한을 제외하고는 보안 정책을 우회할 수 없습니다.

##### 참고 (Note)

보안 정책을 우회할 수 있는 유일한 방법은 사용자에게 `EXEMPT ACCESS POLICY` 시스템 권한이 부여된 경우입니다. 이 권한을 가진 사용자는 데이터베이스의 모든 정책에서 면제되므로 `EXEMPT ACCESS POLICY` 권한은 극도로 주의하여 부여하십시오.

`DBMS_RLS` 패키지는 정책을 생성하고, 정책을 제거하고, 정책을 활성화하고, 정책을 비활성화하는 프로시저를 제공합니다.

Virtual Private Database를 구현하는 프로세스는 다음과 같습니다.

1. 정책 함수를 생성합니다. 함수에는 `VARCHAR2` 타입의 입력 매개변수가 두 개 있어야 합니다. 첫 번째 입력 매개변수는 정책이 적용되는 데이터베이스 객체가 포함된 스키마를 위한 것입니다. 두 번째 입력 매개변수는 해당 데이터베이스 객체의 이름을 위한 것입니다. 함수는 `VARCHAR2` 반환 타입을 가져야 하며 `WHERE` 절 술어(predicate) 형식의 문자열을 반환해야 합니다. 이 술어는 데이터베이스 객체에 작용하는 SQL 명령에 `AND` 조건으로 동적으로 추가됩니다. 따라서 정책 함수 술어를 만족하지 않는 행은 SQL 명령 결과 집합에서 걸러집니다.
2. `ADD_POLICY` 프로시저를 사용하여 새 정책을 정의합니다. 정책은 정책 함수와 데이터베이스 객체의 연결입니다. `ADD_POLICY` 프로시저로 다음을 지정할 수도 있습니다.
   - 정책이 적용되는 SQL 명령의 타입(`INSERT`, `UPDATE`, `DELETE` 또는 `SELECT`)
   - 정책을 생성 시점에 활성화할지 여부
   - 정책이 새로 삽입된 행 또는 업데이트된 행의 수정된 이미지에 적용되는지 여부
3. `ENABLE_POLICY` 프로시저를 사용하여 기존 정책을 비활성화하거나 활성화합니다.
4. `DROP_POLICY` 프로시저를 사용하여 기존 정책을 제거합니다. `DROP_POLICY` 프로시저는 정책 함수나 연결된 데이터베이스 객체를 삭제하지 않습니다.

정책을 생성한 후에는 Oracle 데이터베이스와 호환되는 카탈로그 뷰인 `ALL_POLICIES`, `DBA_POLICIES` 또는 `USER_POLICIES`에서 정책을 볼 수 있습니다. 지원되는 호환 뷰는 [Catalog views](https://www.enterprisedb.com/docs/epas/latest/reference/oracle_compatibility_reference/epas_compat_cat_views/)에 나열되어 있습니다.

`SYS_CONTEXT` 함수는 `DBMS_RLS`와 함께 자주 사용됩니다. 시그니처는 다음과 같습니다.

```sql
SYS_CONTEXT(<namespace>, <attribute>)
```

여기서:

`namespace`는 `VARCHAR2`입니다. 허용되는 유일한 값은 `USERENV`입니다. 다른 값은 `NULL`을 반환합니다.

`attribute`는 `VARCHAR2`입니다. 가능한 값은 다음과 같습니다.

| attribute 값 | 동등한 값 |
| --- | --- |
| `SESSION_USER` | `pg_catalog.session_user` |
| `CURRENT_USER` | `pg_catalog.current_user` |
| `CURRENT_SCHEMA` | `pg_catalog.current_schema` |
| `HOST` | `pg_catalog.inet_host` |
| `IP_ADDRESS` | `pg_catalog.inet_client_addr` |
| `SERVER_HOST` | `pg_catalog.inet_server_addr` |

`DBMS_RLS` 패키지를 설명하는 데 사용되는 예제는 EDB Postgres Advanced Server와 함께 제공되는 샘플 `emp` 테이블의 수정된 복사본과, 해당 테이블에 대한 모든 권한이 부여된 `salesmgr`라는 역할을 기반으로 합니다. `vpemp`라는 이름의 `emp` 테이블 수정 복사본과 `salesmgr` 역할은 다음과 같이 생성할 수 있습니다.

```sql
CREATE TABLE public.vpemp AS SELECT empno, ename, job, sal, comm, deptno
FROM emp;
ALTER TABLE vpemp ADD authid VARCHAR2(12);
UPDATE vpemp SET authid = 'researchmgr' WHERE deptno = 20;
UPDATE vpemp SET authid = 'salesmgr' WHERE deptno = 30;
SELECT * FROM vpemp;
```

## ADD_POLICY

`ADD_POLICY` 프로시저는 정책 함수를 데이터베이스 객체와 연결하여 새 정책을 생성합니다.

이 프로시저를 실행하려면 슈퍼유저여야 합니다.

```sql
ADD_POLICY(<object_schema> VARCHAR2, <object_name> VARCHAR2,
  <policy_name> VARCHAR2, <function_schema> VARCHAR2,
  <policy_function> VARCHAR2
  [, <statement_types> VARCHAR2\
  [, <update_check> BOOLEAN\
  [, <enable> BOOLEAN\
  [, <static_policy> BOOLEAN\
  [, <policy_type> INTEGER\
  [, <long_predicate> BOOLEAN\
  [, <sec_relevant_cols> VARCHAR2\
  [, <sec_relevant_cols_opt> INTEGER ]]]]]]]])
```

### 매개변수 (Parameters)

`object_schema`

정책을 적용할 데이터베이스 객체가 포함된 스키마의 이름입니다.

`object_name`

정책을 적용할 데이터베이스 객체의 이름입니다. 주어진 데이터베이스 객체에는 둘 이상의 정책을 적용할 수 있습니다.

`policy_name`

정책에 지정된 이름입니다. 데이터베이스 객체(`object_schema`와 `object_name`으로 식별됨)와 정책 이름의 조합은 데이터베이스에서 고유해야 합니다.

`function_schema`

정책 함수가 포함된 스키마의 이름입니다.

##### 참고 (Note)

정책 함수는 패키지에 속할 수 있습니다. 이 경우 `function_schema`에는 패키지가 정의된 스키마의 이름이 포함되어야 합니다.

`policy_function`

보안 정책의 규칙을 정의하는 SPL 함수의 이름입니다. 동일한 함수를 둘 이상의 정책에서 지정할 수 있습니다.

##### 참고 (Note)

정책 함수는 패키지에 속할 수 있습니다. 이 경우 `policy_function`에는 점 표기법(즉, `package_name.function_name`)으로 패키지 이름도 포함되어야 합니다.

`statement_types`

정책이 적용되는 SQL 명령의 쉼표로 구분된 목록입니다. 유효한 SQL 명령은 `INSERT`, `UPDATE`, `DELETE`, `SELECT`입니다. 기본값은 `INSERT,UPDATE,DELETE,SELECT`입니다.

##### 참고 (Note)

EDB Postgres Advanced Server는 `INDEX`를 명령문 타입으로 받아들이지만 무시됩니다. EDB Postgres Advanced Server에서는 정책이 인덱스 작업에 적용되지 않습니다.

`update_check`

`INSERT` 및 `UPDATE` SQL 명령에만 적용됩니다.

- `TRUE`로 설정하면 정책이 새로 삽입된 행과 업데이트된 행의 수정된 이미지에 적용됩니다. 새 행이나 수정된 행 중 정책 함수 술어에 따라 자격이 없는 행이 있으면 `INSERT` 또는 `UPDATE` 명령이 예외를 발생시키고 `INSERT` 또는 `UPDATE` 명령에 의해 어떤 행도 삽입되거나 수정되지 않습니다.
- `FALSE`로 설정하면 정책이 새로 삽입된 행이나 업데이트된 행의 수정된 이미지에 적용되지 않습니다. 따라서 새로 삽입된 행이 동일한 정책을 호출하는 후속 SQL 명령의 결과 집합에 나타나지 않을 수 있습니다. 마찬가지로 `UPDATE` 명령 이전에 정책에 따라 자격이 있던 행이 동일한 정책을 호출하는 후속 SQL 명령의 결과 집합에 나타나지 않을 수 있습니다.
- 기본값은 `FALSE`입니다.

`enable`

`TRUE`로 설정하면 정책이 활성화되어 `statement_types` 매개변수로 지정된 SQL 명령에 적용됩니다. `FALSE`로 설정하면 정책이 비활성화되어 어떤 SQL 명령에도 적용되지 않습니다. `ENABLE_POLICY` 프로시저를 사용하여 정책을 활성화할 수 있습니다. 기본값은 `TRUE`입니다.

`static_policy`

Oracle에서 `TRUE`로 설정하면 정책이 _정적(static)_ 입니다. 즉, 정책 함수는 해당 데이터베이스 객체에 대한 정책이 처음 호출될 때 데이터베이스 객체당 한 번 평가됩니다. 결과 정책 함수 술어 문자열은 메모리에 저장되며, 데이터베이스 서버 인스턴스가 실행되는 동안 해당 데이터베이스 객체에 대한 해당 정책의 모든 호출에 재사용됩니다.

- `FALSE`로 설정하면 정책이 _동적(dynamic)_ 입니다. 즉, 정책의 모든 호출에 대해 정책 함수가 재평가되고 정책 함수 술어 문자열이 다시 생성됩니다.

- 기본값은 `FALSE`입니다.

##### 참고 (Note)

Oracle 10g에서는 `static_policy` 매개변수를 대체하기 위한 `policy_type` 매개변수가 도입되었습니다. Oracle에서 `policy_type` 매개변수가 기본값 `NULL`로 설정되어 있지 않으면 `policy_type` 매개변수 설정이 `static_policy` 설정을 재정의합니다.

##### 참고 (Note)

`static_policy` 설정은 EDB Postgres Advanced Server에서 무시됩니다. EDB Postgres Advanced Server는 `static_policy` 매개변수 설정에 관계없이 동적 정책만 구현합니다.

`policy_type`

Oracle에서는 정책 함수가 언제 재평가되는지, 따라서 정책 함수가 반환하는 술어 문자열이 변경되는지 여부와 시점을 결정합니다. 기본값은 `NULL`입니다.

##### 참고 (Note)

이 매개변수 설정은 EDB Postgres Advanced Server에서 무시됩니다. EDB Postgres Advanced Server는 항상 동적 정책을 가정합니다.

`long_predicate`

Oracle에서는 `TRUE`로 설정하면 최대 32K 바이트의 술어를 허용합니다. 그렇지 않으면 술어가 4000바이트로 제한됩니다. 기본값은 `FALSE`입니다.

##### 참고 (Note)

이 매개변수 설정은 EDB Postgres Advanced Server에서 무시됩니다. EDB Postgres Advanced Server 정책 함수는 실질적으로 모든 경우에 무제한 길이의 술어를 반환할 수 있습니다.

`sec_relevant_cols`

`object_name`의 열을 쉼표로 구분한 목록입니다. 나열된 열에 대해 _열 수준 Virtual Private Database(column-level Virtual Private Database)_ 를 제공합니다. `statement_types`에 나열된 타입의 SQL 명령에서 나열된 열 중 하나라도 참조되면 정책이 적용됩니다. 그러한 열이 참조되지 않으면 정책이 적용되지 않습니다.

기본값은 `NULL`이며, 이는 데이터베이스 객체의 모든 열이 `sec_relevant_cols`에 포함된 것과 동일한 효과를 갖습니다.

`sec_relevant_cols_opt`

Oracle에서 `sec_relevant_cols_opt`가 `DBMS_RLS.ALL_ROWS`(값 1의 `INTEGER` 상수)로 설정되면, `sec_relevant_cols`에 나열된 열은 적용된 정책 술어가 거짓인 모든 행에서 `NULL`을 반환합니다. (`sec_relevant_cols_opt`가 `DBMS_RLS.ALL_ROWS`로 설정되지 않으면 이러한 행은 결과 집합에서 전혀 반환되지 않습니다.) 기본값은 `NULL`입니다.

##### 참고 (Note)

EDB Postgres Advanced Server는 `DBMS_RLS.ALL_ROWS`를 지원하지 않습니다. `sec_relevant_cols_opt`가 `DBMS_RLS.ALL_ROWS`(`INTEGER` 값 1)로 설정되면 EDB Postgres Advanced Server는 오류를 발생시킵니다.

### 예제 (Examples)

이 예제는 다음 정책 함수를 사용합니다.

```sql
CREATE OR REPLACE FUNCTION verify_session_user (
    p_schema        VARCHAR2,
    p_object        VARCHAR2
)
RETURN VARCHAR2
IS
BEGIN
    RETURN 'authid = SYS_CONTEXT(''USERENV'', ''SESSION_USER'')';
END;
```

이 함수는 술어 `authid = SYS_CONTEXT('USERENV', 'SESSION_USER')`를 생성하며, 이는 `ADD_POLICY` 프로시저에서 지정된 타입의 SQL 명령의 `WHERE` 절에 추가됩니다.

이는 SQL 명령의 효과를 `authid` 열의 내용이 세션 사용자와 동일한 행으로 제한합니다.

##### 참고 (Note)

이 예제는 `SYS_CONTEXT` 함수를 사용하여 로그인 사용자 이름을 반환합니다. Oracle에서 `SYS_CONTEXT` 함수는 _애플리케이션 컨텍스트(application context)_ 의 속성을 반환하는 데 사용됩니다. `SYS_CONTEXT` 함수의 첫 번째 매개변수는 애플리케이션 컨텍스트의 이름입니다. 두 번째 매개변수는 애플리케이션 컨텍스트에 설정된 속성의 이름입니다. `USERENV`는 현재 세션을 설명하는 특수 내장 네임스페이스입니다. EDB Postgres Advanced Server는 애플리케이션 컨텍스트를 지원하지 않습니다. `SYS_CONTEXT` 함수의 이 특정 사용법만 지원합니다.

다음 익명 블록은 `ADD_POLICY` 프로시저를 호출하여 `secure_update`라는 정책을 생성합니다. 이 정책은 `vpemp` 테이블을 참조하는 `INSERT`, `UPDATE` 또는 `DELETE` SQL 명령이 주어질 때마다 `verify_session_user` 함수를 사용하여 `vpemp` 테이블에 적용됩니다.

```sql
DECLARE
    v_object_schema         VARCHAR2(30) := 'public';
    v_object_name           VARCHAR2(30) := 'vpemp';
    v_policy_name           VARCHAR2(30) := 'secure_update';
    v_function_schema       VARCHAR2(30) := 'enterprisedb';
    v_policy_function       VARCHAR2(30) := 'verify_session_user';
    v_statement_types       VARCHAR2(30) := 'INSERT,UPDATE,DELETE';
    v_update_check          BOOLEAN      := TRUE;
    v_enable                BOOLEAN      := TRUE;
BEGIN
    DBMS_RLS.ADD_POLICY(
        v_object_schema,
        v_object_name,
        v_policy_name,
        v_function_schema,
        v_policy_function,
        v_statement_types,
        v_update_check,
        v_enable
    );
END;
```

## DROP_POLICY

`DROP_POLICY` 프로시저는 기존 정책을 삭제합니다. `DROP_POLICY` 프로시저는 정책과 연결된 정책 함수와 데이터베이스 객체를 삭제하지 않습니다.

이 프로시저를 실행하려면 슈퍼유저여야 합니다.

```sql
DROP_POLICY(<object_schema> VARCHAR2, <object_name> VARCHAR2,
  <policy_name> VARCHAR2)
```

### 매개변수 (Parameters)

`object_schema`

정책이 적용되는 데이터베이스 객체가 포함된 스키마의 이름입니다.

`object_name`

정책이 적용되는 데이터베이스 객체의 이름입니다.

`policy_name`

삭제할 정책의 이름입니다.

### 예제 (Examples)

이 예제는 `public.vpemp` 테이블의 `secure_update` 정책을 삭제합니다.

```sql
DECLARE
    v_object_schema         VARCHAR2(30) := 'public';
    v_object_name           VARCHAR2(30) := 'vpemp';
    v_policy_name           VARCHAR2(30) := 'secure_update';
BEGIN
    DBMS_RLS.DROP_POLICY(
        v_object_schema,
        v_object_name,
        v_policy_name
    );
END;
```

## ENABLE_POLICY

`ENABLE_POLICY` 프로시저는 지정된 데이터베이스 객체에 대한 기존 정책을 활성화하거나 비활성화합니다.

이 프로시저를 실행하려면 슈퍼유저여야 합니다.

```sql
ENABLE_POLICY(<object_schema> VARCHAR2, <object_name> VARCHAR2,
  <policy_name> VARCHAR2, <enable> BOOLEAN)
```

### 매개변수 (Parameters)

`object_schema`

정책이 적용되는 데이터베이스 객체가 포함된 스키마의 이름입니다.

`object_name`

정책이 적용되는 데이터베이스 객체의 이름입니다.

`policy_name`

활성화하거나 비활성화할 정책의 이름입니다.

`enable`

`TRUE`로 설정하면 정책이 활성화됩니다. `FALSE`로 설정하면 정책이 비활성화됩니다.

### 예제 (Examples)

이 예제는 `public.vpemp` 테이블의 `secure_update` 정책을 비활성화합니다.

```sql
DECLARE
    v_object_schema         VARCHAR2(30) := 'public';
    v_object_name           VARCHAR2(30) := 'vpemp';
    v_policy_name           VARCHAR2(30) := 'secure_update';
    v_enable                BOOLEAN := FALSE;
BEGIN
    DBMS_RLS.ENABLE_POLICY(
        v_object_schema,
        v_object_name,
        v_policy_name,
        v_enable
    );
END;
```
