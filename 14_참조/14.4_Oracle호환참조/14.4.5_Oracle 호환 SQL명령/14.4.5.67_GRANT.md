# GRANT — EPAS 18 Reference

> 원문: [EPAS v18 — Reference › Oracle 호환 › 호환 SQL 명령 › GRANT](https://www.enterprisedb.com/docs/epas/latest/reference/oracle_compatibility_reference/epas_compat_sql/64_grant/)
> EPAS v18 공식 문서의 한글 **전문 번역**입니다. 명령·코드 이름은 원문 그대로 보존했습니다.

## 이름 (Name)

`GRANT` — 접근 권한을 정의합니다.

## 구문 개요 (Synopsis)

```sql
GRANT { { SELECT | INSERT | UPDATE | DELETE | REFERENCES }
  [,...] | ALL [ PRIVILEGES ] }
  ON tablename
  TO { username | groupname | PUBLIC } [, ...]
  [ WITH GRANT OPTION ]

GRANT { { INSERT | UPDATE | REFERENCES } (column [, ...]) }
  [, ...]
  ON tablename
  TO { username | groupname | PUBLIC } [, ...]
  [ WITH GRANT OPTION ]

GRANT { { READ | WRITE | ALL [ PRIVILEGES ] } }
  ON DIRECTORY dirname
  TO { username }
  [ WITH GRANT OPTION ]

GRANT { SELECT | ALL [ PRIVILEGES ] }
  ON sequencename
  TO { username | groupname | PUBLIC } [, ...]
  [ WITH GRANT OPTION ]

GRANT { EXECUTE | ALL [ PRIVILEGES ] }
  ON FUNCTION progname
    ( [ [ argmode ] [ argname ] argtype ] [, ...] )
  TO { username | groupname | PUBLIC } [, ...]
  [ WITH GRANT OPTION ]

GRANT { EXECUTE | ALL [ PRIVILEGES ] }
  ON PROCEDURE progname
    [ ( [ [ argmode ] [ argname ] argtype ] [, ...] ) ]
  TO { username | groupname | PUBLIC } [, ...]
  [ WITH GRANT OPTION ]

GRANT { EXECUTE | ALL [ PRIVILEGES ] }
  ON PACKAGE packagename
  TO { username | groupname | PUBLIC } [, ...]
  [ WITH GRANT OPTION ]

GRANT role [, ...]
  TO { username | groupname | PUBLIC } [, ...]
  [ WITH ADMIN OPTION ]

GRANT { CONNECT | RESOURCE | DBA } [, ...]
  TO { username | groupname } [, ...]
  [ WITH ADMIN OPTION ]

GRANT CREATE [ PUBLIC ] DATABASE LINK
  TO { username | groupname }

GRANT DROP PUBLIC DATABASE LINK
  TO { username | groupname }

GRANT EXEMPT ACCESS POLICY
  TO { username | groupname }
```

## 설명 (Description)

`GRANT` 명령에는 다음과 같은 기본 변형이 있습니다.

- 데이터베이스 객체(테이블, 뷰, 시퀀스 또는 프로그램)에 대한 권한을 부여하는 것
- 디렉터리에 대한 권한을 부여하는 것
- 롤에 대한 멤버십을 부여하는 것
- 시스템 권한을 부여하는 것

EDB Postgres Advanced Server에서는 사용자와 그룹의 개념이 _롤(role)_ 이라는 하나의 엔티티 유형으로 통합되었습니다. 이 맥락에서 _사용자(user)_ 는 `LOGIN` 속성을 가진 롤입니다. 이 롤은 세션을 생성하고 애플리케이션에 연결하는 데 사용될 수 있습니다. _그룹(group)_ 은 `LOGIN` 속성이 없는 롤입니다. 이 롤은 세션을 생성하거나 애플리케이션에 연결하는 데 사용할 수 없습니다.

롤은 하나 이상의 다른 롤의 멤버가 될 수 있으므로, 사용자가 그룹에 속한다는 전통적인 개념은 여전히 유효합니다. 그러나 사용자와 그룹의 일반화로 인해, 사용자가 사용자에 "속할" 수 있고, 그룹이 그룹에 "속할" 수 있으며, 그룹이 사용자에 "속할" 수 있어, 롤의 일반적인 다단계 계층 구조를 형성합니다. 사용자 이름과 그룹 이름은 동일한 네임스페이스를 공유합니다. 따라서 `GRANT` 명령에서 권한 수령자(grantee)가 사용자인지 그룹인지 지정할 필요가 없습니다.

## 데이터베이스 객체에 대한 GRANT (GRANT on database objects)

`GRANT` 명령의 이 변형은 롤에게 데이터베이스 객체에 대한 특정 권한을 부여합니다. 이러한 권한은 이미 부여된 권한이 있다면 그 위에 추가됩니다.

`PUBLIC` 키워드는 나중에 생성하는 롤을 포함하여 모든 롤에게 권한을 부여합니다. `PUBLIC`은 항상 모든 롤을 포함하는 암묵적으로 정의된 그룹입니다. 모든 롤은 자신에게 직접 부여된 권한, 자신이 멤버로 속한 롤에 부여된 권한, 그리고 `PUBLIC`에 부여된 권한의 합을 가집니다.

`WITH GRANT OPTION`을 지정하면, 권한을 받은 수령자가 그 권한을 다른 사람에게 부여할 수 있습니다. Grant 옵션은 `PUBLIC`에게 부여되지 않습니다.

객체의 소유자(보통 그것을 생성한 사용자)에게는 권한을 부여할 필요가 없습니다. 소유자는 기본적으로 모든 권한을 가지기 때문입니다. 그러나 소유자는 안전을 위해 자신의 일부 권한을 회수할 수 있습니다. 객체를 삭제하거나 그 정의를 변경할 수 있는 권리는 부여 가능한 권한으로 기술되지 않습니다. 그것은 소유자에게 본래 내재된 것이며 부여하거나 회수할 수 없습니다. 소유자는 또한 그 객체에 대한 모든 grant 옵션을 암묵적으로 가집니다.

객체 유형에 따라 초기 기본 권한에는 `PUBLIC`에 일부 권한을 부여하는 것이 포함될 수 있습니다. 기본값은 테이블의 경우 public 접근 없음이고, 함수, 프로시저, 패키지의 경우 `EXECUTE` 권한입니다. 객체 소유자는 이러한 권한을 회수할 수 있습니다.

##### 참고 (Note)

최대한의 보안을 위해서는 객체를 생성하는 것과 동일한 트랜잭션에서 `REVOKE`를 실행하십시오. 이 방식은 다른 사용자가 객체를 사용할 수 있는 틈이 생기는 것을 방지합니다.

가능한 권한은 다음과 같습니다.

`SELECT`

지정된 테이블, 뷰 또는 시퀀스의 임의의 열에서 `SELECT`를 수행할 수 있게 합니다. 시퀀스의 경우, 이 권한은 `currval` 함수의 사용도 허용합니다.

`INSERT`

지정된 테이블에 새 행을 삽입할 수 있게 합니다.

`UPDATE`

지정된 테이블의 열에 대한 `UPDATE`를 허용합니다. `SELECT ... FOR UPDATE`는 `SELECT` 권한 외에 이 권한도 필요합니다.

`DELETE`

지정된 테이블에서 행을 삭제할 수 있게 합니다.

`REFERENCES`

외래 키 제약 조건을 생성하려면 참조하는 테이블과 참조되는 테이블 모두에 대해 이 권한이 필요합니다.

`EXECUTE`

지정된 패키지, 프로시저 또는 함수의 사용을 허용합니다. 패키지에 적용될 경우, 그 패키지의 모든 public 프로시저, public 함수, public 변수, 레코드, 커서, 그리고 기타 public 객체 및 객체 타입의 사용을 허용합니다. 이것은 함수, 프로시저, 패키지에 적용되는 유일한 유형의 권한입니다.

`EXECUTE` 권한을 부여하기 위한 EDB Postgres Advanced Server 구문은 Oracle 데이터베이스와 완전히 호환되지는 않습니다. EDB Postgres Advanced Server는 프로그램 이름을 `FUNCTION`, `PROCEDURE`, 또는 `PACKAGE` 키워드 중 하나로 한정할 것을 요구합니다. Oracle에서는 이러한 키워드를 생략해야 합니다.

함수의 경우, EDB Postgres Advanced Server는 함수 이름 뒤에 모든 입력(`IN`, `IN OUT`) 인수 데이터 타입을 요구하며, 함수 인수가 없는 경우 빈 괄호도 요구합니다. 프로시저의 경우, 프로시저에 입력 인수가 있다면 모든 입력 인수 데이터 타입을 지정해야 합니다. Oracle에서는 함수와 프로시저의 시그니처를 생략합니다. Oracle에서는 모든 프로그램이 동일한 네임스페이스를 공유하는 반면, EDB Postgres Advanced Server에서는 함수, 프로시저, 패키지가 각각 고유한 네임스페이스를 가져 어느 정도의 프로그램 이름 오버로딩을 허용합니다.

`ALL PRIVILEGES`

사용 가능한 모든 권한을 한 번에 부여합니다.

## 디렉터리에 대한 GRANT (GRANT on directories)

`GRANT` 명령의 이 변형은 사용자에게 디렉터리에 대한 특정 권한을 부여합니다. 가능한 권한은 다음과 같습니다.

`CREATE`

사용자가 디렉터리에 파일을 생성할 수 있게 합니다.

`DROP`

사용자가 디렉터리에서 파일을 제거할 수 있게 합니다.

`READ`

사용자가 읽기 모드로 파일을 열 수 있게 합니다.

`WRITE`

사용자가 읽기 또는 추가(append) 모드로 파일을 생성하거나 열 수 있게 합니다.

## 롤에 대한 GRANT (GRANT on roles)

`GRANT` 명령의 이 변형은 하나 이상의 다른 롤에게 어떤 롤의 멤버십을 부여합니다. 롤의 멤버십은 롤에 부여된 권한을 각 멤버에게 전달하기 때문에 중요합니다.

`WITH ADMIN OPTION`을 지정하면, 멤버는 그 롤의 멤버십을 다른 사람에게 부여하거나 그 롤의 멤버십을 회수할 수 있습니다.

데이터베이스 슈퍼유저는 누구에게나 임의의 롤에 대한 멤버십을 부여하거나 회수할 수 있습니다. `CREATEROLE` 권한을 가진 롤은 슈퍼유저가 아닌 임의의 롤에 대한 멤버십을 부여하거나 회수할 수 있습니다.

미리 정의된 세 가지 롤이 있습니다.

`CONNECT`

`CONNECT` 롤을 부여하는 것은 수령자에게 `LOGIN` 권한을 주는 것과 동일합니다. 부여자(grantor)는 `CREATEROLE` 권한을 가지고 있어야 합니다.

`RESOURCE`

`RESOURCE` 롤을 부여하는 것은 수령자와 같은 이름을 가진 스키마에 대한 `CREATE` 및 `USAGE` 권한을 부여하는 것과 동일합니다. 이 스키마는 부여를 하기 전에 존재해야 합니다. 부여자는 이 스키마에 대한 `CREATE` 또는 `USAGE` 권한을 수령자에게 부여할 권한을 가지고 있어야 합니다.

`DBA`

`DBA` 롤을 부여하는 것은 수령자를 슈퍼유저로 만드는 것과 동일합니다. 부여자는 슈퍼유저여야 합니다.

## 참고 사항 (Notes)

접근 권한을 회수하려면 `REVOKE` 명령을 사용하십시오.

객체의 소유자가 아닌 사용자가 그 객체에 대한 권한을 부여하려고 시도할 때, 그 사용자가 객체에 대한 권한을 전혀 가지고 있지 않으면 명령은 실패합니다. 권한이 하나라도 사용 가능하면 명령은 진행되지만, 그 사용자가 grant 옵션을 가진 권한만 부여합니다. `GRANT ALL PRIVILEGES` 형태는 grant 옵션을 하나도 가지고 있지 않으면 경고를 발생시키고, 다른 형태들은 명령에서 지정한 권한 중 어느 하나에 대한 grant 옵션을 가지고 있지 않으면 경고를 발생시킵니다. 원칙적으로 이러한 설명은 객체 소유자에게도 적용됩니다. 그러나 소유자는 항상 모든 grant 옵션을 가진 것으로 취급되므로 그러한 경우는 결코 발생할 수 없습니다.

데이터베이스 슈퍼유저는 객체 권한 설정과 관계없이 모든 객체에 접근할 수 있습니다. 이것은 Unix 시스템에서의 `root`의 권리에 비견됩니다. `root`와 마찬가지로, 꼭 필요할 때만 슈퍼유저로 작업하십시오.

슈퍼유저가 `GRANT` 또는 `REVOKE` 명령을 실행하면, 그 명령은 마치 영향을 받는 객체의 소유자가 실행한 것처럼 수행됩니다. 특히, 그러한 명령으로 부여된 권한은 마치 객체 소유자가 부여한 것처럼 나타납니다. (롤 멤버십의 경우, 멤버십은 마치 포함하는 롤(containing role)이 부여한 것처럼 나타납니다.)

`GRANT`와 `REVOKE`는 또한 다음에 의해 수행될 수 있습니다.

- 영향을 받는 객체의 소유자는 아니지만 그 객체를 소유한 롤의 멤버인 롤.
- 그 객체에 대해 `WITH GRANT OPTION`으로 권한을 가진 롤의 멤버인 롤. 이 경우, 권한은 그 객체를 소유하거나 `WITH GRANT OPTION`으로 권한을 가진 롤에 의해 부여된 것으로 기록됩니다.

예를 들어, 테이블 `t1`이 롤 `g1`에 의해 소유되고 롤 `u1`이 `g1`의 멤버라면, `u1`은 `t1`에 대한 권한을 `u2`에게 부여할 수 있습니다. 그러나 그러한 권한은 마치 `g1`에 의해 직접 부여된 것처럼 나타납니다. 롤 `g1`의 다른 멤버는 나중에 그것들을 회수할 수 있습니다.

`GRANT`를 실행하는 롤이 둘 이상의 롤 멤버십 경로를 통해 간접적으로 필요한 권한을 가지고 있는 경우, 부여를 수행한 것으로 기록되는 포함하는 롤은 지정되지 않습니다(unspecified). 그러한 경우, 모범 사례는 `SET ROLE`을 사용하여 `GRANT`를 수행하려는 특정 롤이 되는 것입니다.

현재 EDB Postgres Advanced Server는 테이블의 개별 열에 대한 권한 부여나 회수를 지원하지 않습니다. 한 가지 해결 방법은 원하는 열만 가진 뷰를 생성한 다음 그 뷰에 권한을 부여하는 것입니다.

## 예제 (Examples)

테이블 `emp`에 대해 모든 사용자에게 insert 권한을 부여합니다.

```sql
GRANT INSERT ON emp TO PUBLIC;
```

뷰 `salesemp`에 대해 사용자 `mary`에게 사용 가능한 모든 권한을 부여합니다.

디렉터리 `test1`에 대해 사용자 `betty`에게 write 권한을 부여합니다.

```sql
GRANT WRITE ON test1 FROM betty;
```

```sql
GRANT ALL PRIVILEGES ON salesemp TO mary;
```

이 예제는 슈퍼유저나 `emp`의 소유자가 실행하면 모든 권한을 부여하지만, 다른 사람이 실행하면 그 사용자가 grant 옵션을 가진 권한만 부여합니다.

사용자 `joe`에게 롤 `admins`의 멤버십을 부여합니다.

```sql
GRANT admins TO joe;
```

사용자 `joe`에게 `CONNECT` 권한을 부여합니다.

```sql
GRANT CONNECT TO joe;
```

## 시스템 권한에 대한 GRANT (GRANT on system privileges)

`GRANT` 명령의 이 변형은 롤에게 데이터베이스에서 특정 _시스템(system)_ 작업을 수행할 수 있는 능력을 부여합니다. 시스템 권한은 반드시 하나의 스키마 범위 내에 있지는 않은 특정 데이터베이스 객체를 생성하거나 삭제하는 능력과 관련됩니다. 오직 데이터베이스 슈퍼유저만이 시스템 권한을 부여할 수 있습니다.

`CREATE [PUBLIC] DATABASE LINK`

`CREATE [PUBLIC] DATABASE LINK` 권한은 지정된 롤이 데이터베이스 링크를 생성할 수 있게 합니다. `PUBLIC` 키워드를 포함하면 롤이 public 데이터베이스 링크를 생성할 수 있게 합니다. `PUBLIC` 키워드를 생략하면 지정된 롤이 private 데이터베이스 링크를 생성할 수 있게 합니다.

`DROP PUBLIC DATABASE LINK`

`DROP PUBLIC DATABASE LINK` 권한은 롤이 public 데이터베이스 링크를 삭제할 수 있게 합니다. private 데이터베이스 링크를 삭제하는 데는 시스템 권한이 필요하지 않습니다. 링크 소유자 또는 데이터베이스 슈퍼유저가 private 데이터베이스 링크를 삭제할 수 있습니다.

`EXEMPT ACCESS POLICY`

`EXEMPT ACCESS POLICY` 권한은 롤이 대상 데이터베이스 객체와 연결된 어떤 정책 함수(policy function)도 호출하지 않고 SQL 명령을 실행할 수 있게 합니다. 그 롤은 데이터베이스의 모든 보안 정책에서 면제됩니다.

`EXEMPT ACCESS POLICY` 권한은 `EXEMPT ACCESS POLICY` 권한을 가진 롤에 대한 멤버십을 통해 상속될 수 없습니다. 예를 들어, 다음 `GRANT` 명령 시퀀스는 사용자 `joe`가 `EXEMPT ACCESS POLICY` 권한을 획득하는 결과를 가져오지 않습니다. 이는 `joe`가 `EXEMPT ACCESS POLICY` 권한이 부여된 `enterprisedb` 롤에 대한 멤버십을 부여받았음에도 불구하고 그렇습니다.

```sql
GRANT EXEMPT ACCESS POLICY TO enterprisedb;
GRANT enterprisedb TO joe;
```

롤이 `EXEMPT ACCESS POLICY` 권한을 가지고 있으면 시스템 카탈로그 테이블 `pg_authid`의 `rolpolicyexempt` 열이 `true`로 설정됩니다.

## 예제 (Examples)

사용자 `joe`에게 `CREATE PUBLIC DATABASE LINK` 권한을 부여합니다.

```sql
GRANT CREATE PUBLIC DATABASE LINK TO joe;
```

사용자 `joe`에게 `DROP PUBLIC DATABASE LINK` 권한을 부여합니다.

```sql
GRANT DROP PUBLIC DATABASE LINK TO joe;
```

사용자 `joe`에게 `EXEMPT ACCESS POLICY` 권한을 부여합니다.

```sql
GRANT EXEMPT ACCESS POLICY TO joe;
```

## ALTER ROLE 명령을 사용하여 시스템 권한 할당하기 (Using the ALTER ROLE command to assign system privileges)

EDB Postgres Advanced Server의 `ALTER ROLE` 명령은 다음을 할당하는 데 사용할 수 있는 구문도 지원합니다.

- public 또는 private 데이터베이스 링크를 생성하는 데 필요한 권한.
- public 데이터베이스 링크를 삭제하는 데 필요한 권한.
- `EXEMPT ACCESS POLICY` 권한.

`ALTER ROLE` 구문은 Oracle 데이터베이스와 호환되는 해당 명령들과 동등합니다.
