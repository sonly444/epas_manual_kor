# REINDEX — EPAS 18 Reference

## 이름 (Name)

`REINDEX` — 인덱스를 재구성(rebuild)합니다.

## 구문 개요 (Synopsis)

```sql
REINDEX [ ( <option> [, ...] ) ] { INDEX | TABLE | SCHEMA } [ CONCURRENTLY ] <name>
REINDEX [ ( <option> [, ...] ) ] { DATABASE | SYSTEM } [ CONCURRENTLY ] [ <name> ]

여기서 <option>은 다음 중 하나일 수 있습니다:

    CONCURRENTLY [ <boolean> ]
    TABLESPACE <new_tablespace>
    VERBOSE [ <boolean> ]
```

## 설명 (Description)

`REINDEX`는 인덱스가 속한 테이블에 저장된 데이터를 사용하여 인덱스를 다시 빌드하고, 기존 인덱스 사본을 교체합니다. `REINDEX`를 사용하는 상황은 다음과 같습니다.

- 인덱스가 손상되어 더 이상 유효한 데이터를 포함하지 않는 경우. 이론적으로는 발생하지 않아야 하지만, 실제로는 소프트웨어 버그나 하드웨어 장애로 인해 인덱스가 손상될 수 있습니다. `REINDEX`는 복구 방법을 제공합니다.
- 인덱스가 "비대(bloated)"해진 경우, 즉 비어 있거나 거의 비어 있는 페이지를 많이 포함하게 된 경우. 이는 특정한 드문 접근 패턴에서 B-tree 인덱스에 발생할 수 있습니다. `REINDEX`는 죽은 페이지가 없는 새 버전의 인덱스를 작성하여 인덱스의 공간 소비를 줄이는 방법을 제공합니다.
- 인덱스의 저장 파라미터(예: `fillfactor`)를 변경한 뒤, 그 변경이 완전히 적용되었는지 확인하려는 경우.
- `CONCURRENTLY` 옵션으로 인덱스 빌드가 실패하여 인덱스가 "무효(invalid)" 상태로 남은 경우. 이러한 인덱스는 쓸모가 없지만 `REINDEX`로 재구성하는 것이 편리할 수 있습니다. 무효 인덱스에 대한 동시(concurrent) 빌드는 `REINDEX INDEX`만 수행할 수 있다는 점에 유의하십시오.
- 표현식 인덱스가 의존하는 함수의 정의가 변경된 경우. 표현식 인덱스는 인덱스를 빌드하는 시점에 계산된 값을 저장하고 인덱스 검색 시 이를 다시 계산하지 않으므로, 인덱스를 생성한 뒤 함수 정의가 바뀌면 인덱스에는 이전 정의로 계산된 값이 남아 순차 검색 결과와 달라질 수 있습니다. 이 경우 `REINDEX`로 해당 인덱스를 재구성하여 데이터 정합성을 회복합니다. (인라인 가능한 SQL 언어 함수가 `VOLATILE`로 선언되어 있어도 표현식 인덱스가 생성될 수 있는 조건은 [CREATE INDEX](https://www.enterprisedb.com/docs/epas/latest/reference/oracle_compatibility_reference/epas_compat_sql/24_create_index/)의 "표현식 인덱스의 함수 immutability와 재구성" 참고.)

## 파라미터 (Parameters)

`INDEX`

지정한 인덱스를 재생성합니다. 파티션된 인덱스에 사용할 경우 이 형식의 `REINDEX`는 트랜잭션 블록 안에서 실행할 수 없습니다.

`TABLE`

지정한 테이블의 모든 인덱스를 재생성합니다. 테이블에 보조 "TOAST" 테이블이 있으면 그것도 함께 재인덱싱됩니다. 파티션된 테이블에 사용할 경우 이 형식의 `REINDEX`는 트랜잭션 블록 안에서 실행할 수 없습니다.

`SCHEMA`

지정한 스키마의 모든 인덱스를 재생성합니다. 이 스키마의 테이블에 보조 "TOAST" 테이블이 있으면 그것도 함께 재인덱싱됩니다. 공유 시스템 카탈로그의 인덱스도 처리됩니다. 이 형식의 `REINDEX`는 트랜잭션 블록 안에서 실행할 수 없습니다.

`DATABASE`

시스템 카탈로그를 제외한 현재 데이터베이스 내의 모든 인덱스를 재생성합니다. 시스템 카탈로그의 인덱스는 처리되지 않습니다. 이 형식의 `REINDEX`는 트랜잭션 블록 안에서 실행할 수 없습니다.

`SYSTEM`

현재 데이터베이스 내 시스템 카탈로그의 모든 인덱스를 재생성합니다. 공유 시스템 카탈로그의 인덱스가 포함됩니다. 사용자 테이블의 인덱스는 처리되지 않습니다. 이 형식의 `REINDEX`는 트랜잭션 블록 안에서 실행할 수 없습니다.

`name`

재인덱싱할 특정 인덱스·테이블·데이터베이스의 이름입니다. 인덱스와 테이블 이름은 스키마로 한정될 수 있습니다. 현재 `REINDEX DATABASE`와 `REINDEX SYSTEM`은 현재 데이터베이스만 재인덱싱할 수 있습니다. 이들의 파라미터는 선택 사항이며, 지정하는 경우 현재 데이터베이스 이름과 일치해야 합니다.

`CONCURRENTLY`

이 옵션을 사용하면 EDB Postgres Advanced Server는 테이블에 대한 동시 삽입·수정·삭제를 막는 잠금을 걸지 않고 인덱스를 다시 빌드합니다. 반면 표준 인덱스 재빌드는 완료될 때까지 테이블에 대한 쓰기(읽기는 제외)를 잠급니다. 이 옵션을 사용할 때 유의해야 할 몇 가지 주의 사항은 아래의 [온라인 인덱스 재구성(CONCURRENTLY)](#온라인-인덱스-재구성-concurrently) 절을 참고하십시오.

임시 테이블의 경우 다른 세션이 접근할 수 없고 비동시(non-concurrent) 재인덱싱이 더 저렴하므로, `REINDEX`는 항상 비동시로 수행됩니다.

`TABLESPACE`

인덱스를 새 테이블스페이스에 다시 빌드하도록 지정합니다.

`VERBOSE`

각 인덱스가 재인덱싱될 때마다 `INFO` 수준으로 진행 보고서를 출력합니다.

`boolean`

선택한 옵션을 켤지 끌지를 지정합니다. 옵션을 켜려면 `TRUE`, `ON`, `1`을, 끄려면 `FALSE`, `OFF`, `0`을 쓸 수 있습니다. `boolean` 값을 생략할 수도 있으며, 이 경우 `TRUE`로 간주됩니다.

`new_tablespace`

인덱스를 다시 빌드할 대상 테이블스페이스입니다.

## 참고 사항 (Notes)

사용자 테이블의 인덱스가 손상된 것으로 의심되면, `REINDEX INDEX` 또는 `REINDEX TABLE`을 사용하여 해당 인덱스나 테이블의 모든 인덱스를 다시 빌드할 수 있습니다.

시스템 테이블의 인덱스 손상에서 복구해야 하는 경우에는 더 어렵습니다. 이 경우 서버가 의심되는 인덱스를 스스로 사용하지 않는 것이 중요합니다. 안전하게 복구하려면 서버를 `-P` 옵션으로 시작해야 하며, 이 옵션은 시스템 카탈로그 조회에 인덱스를 사용하지 않도록 합니다. 한 가지 방법은 서버를 종료한 뒤 명령줄에 `-P` 옵션을 포함하여 단일 사용자(single-user) 서버를 시작하는 것입니다. 그런 다음 재구성 범위에 따라 `REINDEX DATABASE`, `REINDEX SYSTEM`, `REINDEX TABLE`, `REINDEX INDEX`를 실행할 수 있습니다. 확신이 서지 않으면 `REINDEX SYSTEM`을 사용하여 데이터베이스의 모든 시스템 인덱스를 재구성하십시오. 이후 단일 사용자 서버 세션을 종료하고 일반 서버를 다시 시작합니다.

`REINDEX`는 인덱스 내용을 처음부터 다시 빌드한다는 점에서 인덱스를 삭제한 뒤 다시 생성하는 것과 유사합니다. 그러나 잠금 관점에서는 상당히 다릅니다. `REINDEX`는 인덱스가 속한 테이블의 쓰기는 잠그지만 읽기는 잠그지 않습니다. 또한 처리 중인 특정 인덱스에 대해 `ACCESS EXCLUSIVE` 잠금을 획득하며, 이는 해당 인덱스를 사용하려는 읽기를 차단합니다. 반면 `DROP INDEX`는 상위 테이블에 대해 순간적으로 `ACCESS EXCLUSIVE` 잠금을 획득하여 쓰기와 읽기를 모두 차단합니다.

`REINDEX`가 실행되는 동안 `search_path`는 일시적으로 `pg_catalog, pg_temp`로 변경됩니다.

단일 인덱스나 테이블을 재인덱싱하려면 해당 테이블에 대한 `MAINTAIN` 권한이 필요합니다. 스키마나 데이터베이스를 재인덱싱하려면 해당 스키마·데이터베이스의 소유자이거나 `pg_maintain` 역할의 권한이 있어야 합니다.

파티션된 인덱스나 파티션된 테이블의 재인덱싱은 각각 `REINDEX INDEX` 또는 `REINDEX TABLE`로 지원됩니다. 지정한 파티션 관계의 각 파티션은 별도의 트랜잭션에서 재인덱싱됩니다. 이러한 명령은 파티션된 테이블이나 인덱스를 대상으로 할 때 트랜잭션 블록 안에서 사용할 수 없습니다.

## 온라인 인덱스 재구성 (CONCURRENTLY)

인덱스를 다시 빌드하면 데이터베이스의 정상적인 운영에 영향을 줄 수 있습니다. 일반적으로 EDB Postgres Advanced Server는 인덱스를 다시 빌드할 테이블을 쓰기에 대해 잠그고, 테이블을 한 번 스캔하여 전체 인덱스 빌드를 수행합니다. 다른 트랜잭션은 여전히 테이블을 읽을 수 있지만, 테이블의 행을 삽입·수정·삭제하려고 하면 인덱스 재빌드가 끝날 때까지 차단됩니다. 이는 운영 중인 프로덕션 데이터베이스에서는 심각한 영향을 줄 수 있습니다.

EDB Postgres Advanced Server는 쓰기 잠금을 최소화하여 인덱스를 다시 빌드하는 방식을 지원합니다. 이 방식은 `REINDEX`의 `CONCURRENTLY` 옵션을 지정하여 사용합니다. 이 옵션을 사용하면 서버는 다시 빌드해야 하는 각 인덱스에 대해 테이블을 두 번 스캔해야 하며, 인덱스를 잠재적으로 사용할 수 있는 기존의 모든 트랜잭션이 종료될 때까지 기다려야 합니다. 이 방식은 표준 인덱스 재빌드보다 총 작업량이 많고 완료까지 훨씬 오래 걸립니다. 그러나 인덱스를 다시 빌드하는 동안 정상적인 작업을 계속할 수 있으므로, 프로덕션 환경에서 인덱스를 다시 빌드할 때 유용합니다.

인덱스를 다시 빌드하는 도중 고유 인덱스의 고유성 위반과 같은 문제가 발생하면 `REINDEX` 명령은 실패하고, 기존 인덱스에 더해 "무효(invalid)" 상태의 새 인덱스를 남깁니다. 이 인덱스는 불완전할 수 있으므로 쿼리에서는 무시되지만, 갱신 오버헤드는 계속 발생시킵니다. psql의 `\d` 명령은 이러한 인덱스를 `INVALID`로 보고합니다. `INVALID`로 표시된 인덱스의 접미사가 `_ccnew`이면 동시 작업 중 생성된 임시 인덱스에 해당하며, 권장 복구 방법은 `DROP INDEX`로 삭제한 뒤 `REINDEX CONCURRENTLY`를 다시 시도하는 것입니다. 접미사가 `_ccold`이면 삭제되지 못한 원본 인덱스에 해당하며, 재빌드 자체는 성공했으므로 해당 인덱스를 삭제하면 됩니다.

정규(regular) 인덱스 빌드는 동일한 테이블에서 다른 정규 인덱스 빌드가 동시에 수행되는 것을 허용하지만, 한 테이블에서는 한 번에 하나의 동시 인덱스 빌드만 수행될 수 있습니다. 또한 정규 `REINDEX TABLE`이나 `REINDEX INDEX` 명령은 트랜잭션 블록 안에서 수행될 수 있지만 `REINDEX CONCURRENTLY`는 그럴 수 없습니다.

`REINDEX SYSTEM`은 시스템 카탈로그를 동시에 재인덱싱할 수 없으므로 `CONCURRENTLY`를 지원하지 않습니다. 또한 배제 제약 조건(exclusion constraint)을 위한 인덱스는 동시에 재인덱싱할 수 없습니다.

## 예제 (Examples)

단일 인덱스를 다시 빌드하려면:

```sql
REINDEX INDEX my_index;
```

테이블 `my_table`의 모든 인덱스를 다시 빌드하려면:

```sql
REINDEX TABLE my_table;
```

관련 관계에 대한 읽기·쓰기 작업을 차단하지 않고(온라인으로) 테이블의 인덱스를 다시 빌드하려면:

```sql
REINDEX TABLE CONCURRENTLY my_broken_table;
```
